## 今天的核心：三段接力，两个编号系统

### 接力棒一比 UART 还清晰

```text
ControlTask（5 ms）      写目标：setangle / setspeed / setPos
        ↓
MotorUpdateTask（2 ms）  读反馈 → 跑 PID → 算电流 → 写进 temp_data
        ↓
CanTransimtTask（1 ms）  私有 can_div 计数 %3，三帧轮发：
                         0 = 达妙 ×2，1 = 0x1FF 帧，2 = 0x200 帧
```

每一拍只干一件事，目标值、电流值、报文三者分离。对比第 1 到 6 课的 UART 链路也是这个形状：搬运的归搬运，解析的归解析。

### 一帧 CAN 长什么样，电机怎么认

CAN 帧 = 一个 ID（标准帧 11 位）+ 最多 8 字节数据。大疆电机的约定：

- ID `0x200` 控制拨码 1 到 4 的电机；
- ID `0x1FF` 控制拨码 5 到 8 的电机；
- 每个电机占 2 字节电流，**高字节在前**（`motor.cpp:152-153`）。

所以 `can.temp_data[16]` = 8 个电机 × 2 字节，`CanTransimtTask` 分两次发：`0x200` 带前 8 字节（`temp_data`），`0x1FF` 带后 8 字节（`temp_data + 8`，`taskslist.cpp:121-126`）。一帧最多 8 字节，16 字节必须拆两帧。

### 两套编号，在 Ontimer 里对齐

- **虚拟 ID**：`motor.h:14` 的 `ID1 = 0x205` 起，只用来算索引 `this->ID - ID1`（`motor.cpp:66`），决定电流写进 `temp_data` 的第几个两字节；
- **真实反馈 ID**：`0x200 + 拨码`，`HAL_CAN_RxCpltCallback` 用它算 `id - 0x201` 落到 `can.data` 第几行（`can.cpp`）。

拨码 3 的电机：反馈 ID `0x203` 落在 `data[2]`；要用它就得是虚拟 `ID3 = 0x207`，Ontimer 索引也是 2，电流写 `temp_data[4..5]`，随 `0x200` 帧发出。两套编号在“拨码 1-4 走 0x200、5-8 走 0x1FF”这个约定下自然对齐，这就是电机 ID 叫“虚拟 ID”的原因。

### 反馈是广播，不是问答

电机按自己的 ID 周期性往总线上广播状态帧，主控的过滤器设成全收（掩码 0，`can.cpp` 的 `InitFilter`），`HAL_CAN_RxCpltCallback` 按 ID 分拣：`0x201` 到 `0x208` 进 `can.data[slot]`，其余按 `Data[0]` 低 4 位匹配达妙。反馈帧 8 字节的布局：角度 2、速度 2、电流 2、温度 1（`motor.cpp:74-77`）。`has_feedback` 的判据是温度或角度非零——上电时的零缓冲不会误置位。

### 一个已经踩过的坑：计数器只能在一处递增

`taskslist.cpp:103-109` 的注释记着：原来用全局 `timer.counter % 3`，而这个变量在 TIM3 中断和本任务里各加一次，余数步进被两个时钟源的相位影响，相位一漂就变成“某帧连发两次、另一帧隔 6 ms”——对电流环就是控制周期抖动。改成任务私有的 `static uint8_t can_div` 后与任何中断无关。

### 和 UART 对比着记（通用知识）

UART 是点对点、靠波特率同步、软件定义帧格式；CAN 是总线、靠 ID 寻址、硬件做仲裁和 CRC、多节点广播。第 1 到 6 课那套“怎么判一帧结束、怎么拼半帧”在 CAN 里不存在——硬件全包了，软件只需要认 ID。

## 本次要点

- 三段接力：ControlTask 写目标（5 ms）、MotorUpdateTask 算电流（2 ms）、CanTransimtTask 发报文（1 ms，每组 3 ms 一帧）。
- 大疆电机报文约定：`0x200` 带拨码 1-4，`0x1FF` 带 5-8，每电机 2 字节电流、高字节在前。
- 虚拟 ID 算发送索引，真实反馈 ID 算接收槽位，两套编号靠拨码约定对齐。
- 反馈是广播：过滤器全收，回调按 ID 分拣；角度/速度/电流/温度按固定偏移解包。
- 分频计数器必须只在一处递增，否则周期受多时钟源相位影响而抖动。
