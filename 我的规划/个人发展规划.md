# 个人发展规划

> **现阶段主线：以嵌入式软件为根基，通过机器人项目练习软硬件协同，再向 Linux／机器人系统或端侧 AI 延伸。**
>
> 先用三个月做出一个自己能解释、能复现的小成果，再决定下一阶段加深哪个方向。

## 1. 我从哪里出发

这份规划结合已有笔记和此前交流整理。暂按“厦大计科、大二上、参与 RoboMaster 电控、对硬件和软硬结合更感兴趣”安排；年级、课程完成情况和每周时间有变化时，相应顺延。

| 已有经历或倾向 | 对规划的意义 |
| --- | --- |
| 接触过 C/C++、数据结构和机器人电控工程代码 | 从真实模块继续深入，基础薄弱处随项目补齐 |
| 正在接触 STM32、通信协议、调试和实车标定 | 把通信、时序、控制和故障排查做成第一项可证明的能力 |
| 有 ROS 2 小车相关项目经历 | 后续可以承接 Linux 与 MCU 的整机联调 |
| 关注 Human+、具身智能和端侧 AI | 保留探索空间，先通过小实验验证兴趣和投入能力 |
| 接触 LegalAgent，想亲手提交小改动 | 用一次小贡献练习 Git、阅读代码、验证和协作 |

这些经历说明我有起点，不代表已经熟练掌握。下一步要把“接触过”变成“独立完成过，而且有记录”。

## 2. 方向怎么选

### 当前主攻：嵌入式软件与机器人底层通信

未来三个月优先提高：C/C++、STM32、中断与 DMA、任务协作、串口／CAN、数据记录、基础电机控制与调试。

目标是能独立负责一个边界清楚的小模块，解释它的输入、输出、运行周期、异常处理和验证方法。

### 下一步延伸：Linux 与机器人系统

当 MCU 侧的小模块能稳定工作后，学习 Linux 下的 C++／Python 工具、串口通信、进程线程和 ROS 2，把上位机与下位机连成完整流程。

“机器人系统工程师”可以作为长期方向；本科阶段先积累驱动接入、通信桥接、日志诊断和整机联调的具体能力。

### 可选加分：端侧 AI 或 IMU 数据处理

有明确任务、设备和时间时，做一个小模型推理或 IMU 数据处理实验。先掌握输入输出、预处理、基础模型原理和评估，再按需要学习部署与优化。

目前不同时铺开 MCU TinyML、Jetson、RKNN、CUDA、强化学习和大模型。选一个实际用得上的平台即可。

**职业选择依据真实岗位要求和自己的实践体验。** 旧笔记中的“本科一定够”“某方向竞争极小”“薪资必然更高”等判断，不作为决策依据；计科背景也不妨碍申请嵌入式软件岗位。

## 3. 接下来十二周：2026-10-30—2027-01-21

这一轮只有一个主项目：**从现有机器人项目中选一条通信／数据链路，完成理解、记录、验证和一个小改进。** 优先选队伍确实需要、有人能评审、自己能接触设备的模块。

默认选题：机器人状态数据的接收、解析、记录和离线回放。若团队已有安排，就替换成同等规模的真实任务。

| 阶段                | 重点行动                                        | 留下的成果                         | 完成标准                             |
| ----------------- | ------------------------------------------- | ----------------------------- | -------------------------------- |
| 第1—2周：10/30—11/12 | 和队友确认模块边界；追踪从串口／CAN 接收到数据被使用的过程；跑通现有构建和调试流程 | 一页数据流说明、一次构建记录、一份真实或明确标注的模拟数据 | 能指着代码解释数据经过哪些函数／任务，在哪检查长度、单位和有效性 |
| 第3—4周：11/13—11/26 | 亲手实现或完善一个小功能，例如协议解析工具、接收统计或状态日志             | 小范围代码改动、输入样例、运行结果             | 正常输入可复现；坏包、截断或超时有明确处理；能解释自己的改动   |
| 第5—8周：11/27—12/24 | 用 Python 记录、绘图和回放；围绕一个实际问题做测量               | 日志、曲线、一次问题定位记录                | 能从保存的数据复现现象，用结果说明问题；有设备时补一次真实采集  |
| 第9—12周：12/25—1/21 | 整理说明、补缺失验证、演示与复盘；根据期末安排压缩范围                 | README、关键结果、短演示、下一步清单         | 同学按说明能运行；自己能在5分钟内讲清需求、实现、问题和限制   |

期末周优先复习，暂停新增功能；阶段可以顺延。设备暂不可用时先完成离线样例和工具，明确标注哪些结果来自模拟、哪些来自真机。

### 主项目的验收方式

根据实际模块选其中三至四项，不为了凑指标而增加功能。

| 检查项 | 方法 | 输出与通过标准 |
| --- | --- | --- |
| 数据一致性 | 对照已知输入或发送端记录检查解析结果 | 字段、符号、单位与约定一致；记录异常样例 |
| 异常输入 | 人为加入截断、错误校验、额外字节或断连 | 无越界／崩溃；丢弃或恢复行为符合模块约定 |
| 连续运行 | 在约定负载下记录运行时间、计数和异常 | 先写明测试时长与允许阈值，再判断是否通过 |
| 频率与延迟 | 记录采样点和时间戳，说明时钟来源 | 有分布或曲线；不把循环周期直接当作端到端延迟 |
| 故障恢复 | 按测试条件断开、重连或停止输入 | 恢复和超时行为可复现，符合事先约定 |

涉及运动时，测试前与队友明确限幅、急停和场地条件；涉及发射机构的功能不纳入这个入门成果。编译成功、离线回放和真机通过分别记录。

## 6. 多个项目怎样取舍

| 项目或机会 | 当前定位 | 投入边界 |
| --- | --- | --- |
| RoboMaster／Sentinel | 近期主项目，练通信、时序、控制与调试 | 一次负责一个清楚的模块；把自己的修改和验证留下记录 |
| ROS 2 小车 | 下一阶段承接系统集成 | 尽量复用通信工具、日志和已有硬件，与主项目顺序推进 |
| Human+／实验室探索 | 可选方向验证 | 有余力再做一个 IMU／数据处理小实验；正式加入前核实当前要求与实际时间 |
| LegalAgent | 可选的软件协作练习 | 选择一次小贡献，完成阅读、修改、验证和评审；挤占主线时暂停 |
| 课程项目 | 优先满足教学要求，复用通用方法 | 用来练规范、表达和工具，不自动扩展成长期项目 |

实验室探索先回答三个问题：我对具体任务是否有兴趣？能否持续投入？能否做出一个可展示结果？三个月后再决定是否扩大投入。

科研／端侧 AI 试验必须占用同一个时间预算，加入它时就减少其他任务。正式加入团队前重新核对当期要求，不凭旧招聘信息安排承诺。

## 7. 每周怎样执行

先试行两周：**课程之外，每周安排6—8小时用于这份规划，包含已投入的机器人项目时间。** 如果比赛任务已超过这一额度，暂停额外学习支线，直接从比赛任务中提炼成果。

8小时参考分配：主项目4小时、基础补习2小时、数据整理／文档1小时、复盘与下周安排1小时。只有6小时时优先缩减支线，不压缩必要的验证。

- 每周只定一个最重要的成果，例如“一段可运行代码”“一张实测曲线”“一份故障定位记录”。
- 新工具只在当前任务确实需要时引入；先使用现有开发板、调试器和电脑。
- AI 可用于解释、查错和讨论方案；关键代码亲手实现，合并前能逐段解释并验证。
- 连续两周无法完成时，缩小任务或延后节点；保留正常睡眠、运动和休息。
- 每月找队友、学长或老师看一次成果，得到一条具体反馈。

## 8. 什么时候调整方向

2026年11月底先检查能否持续执行，2027年1月下旬做第一次完整复盘；再按学期调整。

- 更喜欢 MCU、外设、时序和现场调试：加深 C、RTOS、通信与可靠性，按真实岗位决定是否进入驱动／BSP。
- 更喜欢把多个模块连接起来、分析整机数据：加深 C++、Linux、ROS 2、并发与系统诊断。
- 确实喜欢数据和模型，且基础链路已经完成：增加一个端侧推理或 IMU 算法实验，记录准确性、延迟和资源消耗。
- 更喜欢理论推导与研究问题：结合课程表现和导师反馈，重新评估科研与升学投入。

每次调整都参考三类证据：亲手做过的体验、外部反馈、近期真实岗位／团队要求。准备实习前收集约10条目标岗位描述，区分必需与加分项，再补最常出现的缺口。
