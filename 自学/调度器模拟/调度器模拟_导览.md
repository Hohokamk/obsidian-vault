## 你会亲手摸到哪些数据结构

### 1. 链表 —— `DList`
双向链表 + 哨兵头（`sentinel`），环形。头尾插入删除 O(1)。FreeRTOS 的 `List_t` 就是它。
- 就绪队列 = 一个链表的**数组**，下标就是优先级：`ready_lists[priority]`。这是"数组当索引、链表做桶"的经典组合。

### 2. 有序链表 —— `delayed_list`
按唤醒时刻 `wake_time` 升序插入。调度器每次只看**表头**：最早到期的任务醒没醒。这就是"看表头"的 O(1) 思路。

### 3. 优先队列 / 堆 —— `MinHeap`
对照实验：所有就绪任务扔进小顶堆，每次 O(log n) 挑最高优先级。和链表数组版一比，你会亲眼看到**"选哪种结构 = 做一次权衡"**。

### 4. 状态机 —— `task.state`
`READY → RUNNING → DELAYED → READY → DONE`，一张带环的有向图。这就是离散数学图论里的**有限状态机**，也是你电赛/哨兵按键消抖背后的同款模型。

## 对照实验：两个调度器

同一份任务脚本，两个内核各跑一遍：

- **链表数组版**：抢占 + 时间片轮转 → LED流水灯和舵机控制（同优先级 2）**轮流**吃 CPU
- **小顶堆版**：纯优先级抢占、无时间片 → 同优先级的活儿**干完一件才换**

看 `任务小结` 里"就绪等CPU"的 tick 数，两个版本对同优先级任务的待遇明显不同。

## 跑之前先猜（30 秒热身）

下面 4 个任务，优先级 3/2/2/1，时间片 3 tick：

```
按键扫描：跑2 tick → 睡5 tick，重复4次
LED流水灯：跑4 → 睡6，重复3次
舵机控制：跑3 → 睡7，重复3次
串口上报：跑5 → 睡3，重复2次
```

- 猜：串口上报（最低优先级）前 10 个 tick 是什么颜色？它为什么"总被抢"？

## 跑完之后回答

1. 哪个任务"就绪等CPU"时间最长？为什么它值得等？
