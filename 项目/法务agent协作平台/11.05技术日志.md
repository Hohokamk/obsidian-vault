### 当前公共法源 Schema 复核

- 数据库核心是四张表：`la_corpus_documents` 保存资料目录与当前版本指针，`la_corpus_revisions` 保存不可变版本、整份 Markdown 的 SHA-256、BlobStore 对象地址、字节数、元数据和检索正文；`la_corpus_jobs` 保存维护任务，`la_corpus_schedules` 保存合法定时任务。
- 稳定 ID 由应用生成：`documentId = lc_ + SHA-256(corpus:sourceId)`，`revisionId = lcr_ + SHA-256(documentId:sha256)`。同一 `(corpus,source_id)` 只有一个目录；同一 `(document_id,sha256)` 只有一个版本。`current_revision_id` 表示当前发布给平台和 Agent 的版本，不是法律效力状态。
- 原文字节以不可变对象保存到 `legal-corpus/{corpus}/{documentId}/{sha256}.md`，PostgreSQL 的 `object_ref` 只保存对象地址；读取固定版本时同时校验字节数和 SHA-256。`search_text` 保存去掉 front matter 的 Markdown 正文，并使用 `pg_trgm` GIN 索引辅助关键词检索。
- 写入入口是 `LegalCorpusStore.put()`。`PUBLISH` 新增版本后移动当前指针，`BACKFILL` 只补历史、不移动当前指针；相同文档和 hash 重放返回 `changed=false`，传入 `jobId` 时写入事务还要求任务仍为 `RUNNING` 且未被取消。
- 以 `apps/server/src/legal-corpus/migration.ts` 当前源码为准确认表结构和约束；本轮仅做只读检查，未修改仓库源码，也未重新运行迁移或测试。

### 数据库与运行进程的关系

- 进程与 PostgreSQL 之间不是“只有一个业务接口”：最底层是 PostgreSQL Wire Protocol 和 TCP 连接；Node 侧由 `pg` 的 `Pool` 管理连接；应用层再通过 `PostgresStore`、各领域 Store/Service 封装查询和事务。Web 访问 API 的 HTTP 接口是另一条链路，不能和进程访问数据库的链路混为一谈。
- `compose.yaml` 只定义 PostgreSQL 16 容器和数据卷，不运行 Node API 或 Worker。API 与 Worker 是独立进程：根 `package.json` 中 `dev` 启动 `apps/server/src/http/main.ts`，`worker` 启动 `apps/server/src/worker.ts`，`corpus:worker` 启动 `apps/server/src/legal-corpus/worker-main.ts`。
- API 和主 Worker 都从 `DATABASE_URL` 读取同一个数据库地址并调用 `createServices()`；主 Worker 使用同一组 Store，但不是由 API 进程 fork 出来的子进程。公共法源维护可配置独立的 `LEGALAGENT_CORPUS_DATABASE_URL`，未配置时回退到 `DATABASE_URL`；配置独立库时，API 与 corpus Worker 必须指向同一资料库并访问同一 BlobStore。
- `PostgresStore` 在构造时创建 `Pool`，默认最多 10 个连接、连接超时 1500ms、查询超时 5000ms，并通过 `search_path` 选择 schema；它把 Pool 交给 Drizzle。Drizzle 在这里主要提供 `sql` 构造、参数绑定和事务入口，表名、列名、约束和业务 SQL 仍由仓库中的迁移及查询代码明确维护。
- 所谓“数据库适应代码”或“代码适应数据库”都不是单向自动发生。设计时由业务代码和领域契约提出所需数据形态，数据库 schema 为这些需求提供持久化、外键、唯一约束和状态检查；运行时代码必须按现有表名列名和约束发出 SQL。只改 TypeScript 字段不会自动改表，只改表也不会自动更新代码，因此两者通过迁移及契约测试共同演进。
- 迁移方向是“数据库实例追到代码仓库声明的版本”：`scripts/migrate-database.ts` 调用 `PostgresStore.migrate()`，后者按固定顺序执行 `CORE_MIGRATION`、材料、恢复、资料库等 DDL，并用 `CREATE TABLE/INDEX IF NOT EXISTS`、`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 和约束检查保持可重复执行。应用启动只创建服务，不在 `readConfig()`/`createServices()` 中执行迁移或探测数据库。
- 查询不是“代码直接读取数据库文件”。应用先构造参数化 SQL，例如 `LegalCorpusStore.search()` 使用 `ILIKE $2` 匹配标题和 `search_text`，再由 `pg` 经连接池发给 PostgreSQL；数据库解析 SQL、生成执行计划、选择顺序扫描或 GIN/trigram 索引、读取表和索引、应用过滤/排序/`LIMIT`，最后把结果集返回 Node，代码再映射字段并用领域 schema 校验。
- 当前法源检索是关键词/子串检索，不是 PostgreSQL `tsvector` 全文检索，也不是向量检索或 BM25。`la_corpus_revisions_search_trgm` 可辅助 `search_text ILIKE '%关键词%'`；但 `metadata->>'title'` 没有单独索引，实际执行是否走索引仍应由 `EXPLAIN (ANALYZE, BUFFERS)` 在真实数据上验证，不能只看 DDL 推断性能。
- 数据库还承担进程间协调：`la_runs` 用状态、`lease_owner`、`lease_token`、`lease_until` 和 `attempt_count` 表示谁暂时拥有任务；Worker 通过 `FOR UPDATE SKIP LOCKED` 原子领取一行，API 与 Worker 不需要直接 RPC。`completeRun()` 在同一事务中写业务表、状态、事件和 outbox，任一步失败则整体回滚；corpus Worker 还用 PostgreSQL advisory lock 串行化维护任务。
- `jsonb` 不是“没有 schema”：它适合保存灵活或整体版本化的 body，但代码仍用 Zod/领域 schema 做运行时校验；关系字段、状态枚举、唯一性和跨表关联由 PostgreSQL 约束兜底。两者分工是“数据库保证可落盘的硬约束，应用保证业务语义和授权边界”。

### Schema 与接口契约冻结评估

- **结论：`legal-corpus-v1` 已完成项目内口径冻结。** 冻结范围是四表 PostgreSQL Schema、稳定 ID、不可变版本、内部 `legal-corpus-write/v1` 契约和六个只读 API；不包含生产部署或朱侧联调验收。
- **BACKFILL 已收紧。** 首次见到的文档不能直接 `BACKFILL`；只有已有当前发布版本的文档才能补历史版本。历史版本重放返回 `changed=false`、`published=false`，v1 不支持回滚或把旧 revision 重新发布为当前版本。
- **写入契约已正式化。** 请求、结果和错误码由 `write-contract.ts` 运行时校验，通过 `jobId` 写入时要求任务仍为 `RUNNING` 且未取消；维护 Worker 是唯一自动写者。
- **授权口径已统一。** 六个法源 GET 操作的契约均声明有效组织绑定要求，维护接口额外要求组织管理员。维护响应禁止返回原始 `summary`，只允许脱敏 `failurePreview`。
- 当前仍没有新的 Linux CI 结果，也未创建提交或推送。冻结是接口语义冻结，不把当前混合工作树称为已合并或已部署；提交后仍应以 CI 和双方样例联调作为交付证据。
- 兼容规则：新增字段可走 v1.x；删除或改名、改变字段语义、ID、发布语义、权限或固定版本完整性行为时必须升级 v2。
