**存储边界：** 已提交基线中的 PostgreSQL 保存 `la_corpus_documents`、`la_corpus_revisions`、`la_corpus_jobs` 和 `la_corpus_schedules`，即目录、版本、hash、`object_ref`、字节数、JSON 元数据和运维任务，Markdown 正文字节保存在 BlobStore。但核对期间工作区出现了未提交的检索改动：`la_corpus_revisions` 新增 `search_text`，`LegalCorpusStore.put()` 会把完整 Markdown 文本写进 PostgreSQL，同时创建 `pg_trgm` GIN 索引。若这组改动保留并执行迁移，数据库会额外保存一份全文，不再只是目录和元数据；BlobStore 仍保存原始字节。

**7G 判断：** 对未包含 `search_text` 的已提交基线，按当前 4 条版本样本行大小推算，7,804 条文档加 7,804 个当前版本预计占数据库约 30～60 MB。对当前未提交全文检索改动，实际把全部 7,804 份 Markdown 载入事务内临时表并建立 `pg_trgm` GIN 索引后，正文堆与 TOAST 为 39 MB、索引为 118 MB、两者合计 157 MB；该临时表已在 `ROLLBACK` 后消失，主库仍为 10 MB。再叠加约 10 MB metadata JSON、文档行、既有约束索引和任务表，整库预计约 180～250 MB，保守预留 300 MB 已足够。7G 配额即使采用当前全文入库方案仍约有 20 倍以上余量。

若 7G 指整台机器的总磁盘，还需要同时计算仓库源快照约 100 MiB、BlobStore 正文约 75 MiB、默认导入工作目录的正文副本约 75 MiB，以及采用全文检索后的数据库约 180～250 MB，总计约 430～500 MB。44 份附件当前不进入 Markdown 导入器和 BlobStore；若以后纳入，再增加约 22.5 MiB。

**部署限制：** 本地 `storageDriver=local` 依赖持久磁盘；容器重建会丢失未挂载的 `.local/objects`。云端应使用 S3 兼容存储或挂载持久卷，不能假定 PostgreSQL 的 7G 配额也保存了正文对象。历史版本、附件、OCR/PDF、全文检索索引和未来 RAG 向量会带来独立增量，后续应按实际数据库 `pg_database_size` 和 BlobStore 容量分别监控。

## 问题与排查

### 现象

`dev`、`worker`、Web 和 PostgreSQL 都已启动，输入 `.local/demo-credentials.json` 中的账号密码后仍然无法登录。

### 实测证据

- 使用同一组账号密码，直接向 `http://127.0.0.1:3310/api/auth/sign-in/email` 发送请求，返回 HTTP 200，并返回同一个用户 ID。
- 请求携带浏览器 origin `http://127.0.0.1:5173` 时，返回 HTTP 403：`Invalid origin` / `INVALID_ORIGIN`。
- Vite 代理只转发请求，不会把浏览器的 `Origin` 改成后端地址，因此 API 看到的是 `5173`，而 API 的 `AUTH_URL` 仍为 `.env.local` 中的 `3310`。

### 结论

不是数据库账号不存在，也不是初始化密码错误。账号、密码和数据库身份是匹配的；失败发生在登录请求的 origin 校验层。

### 修复方式

在启动 API 和 Worker 的终端中显式设置同一个浏览器 origin，然后重启这两个进程。PowerShell 示例：

```powershell
$env:AUTH_URL = 'http://127.0.0.1:5173'
npm run dev
```

Worker 使用同样的 `AUTH_URL`：

```powershell
$env:AUTH_URL = 'http://127.0.0.1:5173'
npm run worker
```

Web 仍按原方式启动。修复后不需要重新初始化数据库，也不需要重新生成账号。

## GitHub 协作

### Fork 与远程仓库关系

- GitHub 的 fork 是账号名下的远端仓库副本，不会自动替换本地已有克隆的 remote。
- 本次检查时，`D:\03_Projects\LegalAgent` 的 `origin` 仍为原项目 `git@github.com:dercaft/LegalAgent.git`，当前分支为 `main`，工作区已有未提交修改。
- 标准协作方式是把 fork 设为 `origin`，把原项目设为 `upstream`；每个事项从最新 `upstream/main` 建立独立分支。
- 本地完成修改、测试和 commit 后，将分支 push 到 fork，再在 GitHub 上从 fork 分支向原项目 `main` 发起 PR。
- PR 不是“上传整个仓库”或直接在网页替换文件；它比较 fork 分支与原项目目标分支的提交差异。后续评审修改继续提交到同一分支并 push，PR 会自动更新。

### 典型命令

```bash
git remote rename origin upstream
git remote add origin git@github.com:<你的用户名>/LegalAgent.git
git fetch upstream
git switch main
git pull --ff-only upstream main
git push -u origin main
git switch -c feat/short-description
```

修改并验证后：

```bash
git add <变更文件>
git commit -m "feat: describe the change"
git push -u origin feat/short-description
```

之后在 GitHub 打开 fork 页面，选择该分支并点击 `Compare & pull request`，目标选择原项目的 `main`。PR 描述应写明问题、行为变化、涉及范围和实际测试；评审期间不要通过关闭旧 PR、重建新分支来掩盖每轮修改。

### 合并上游更新

```bash
git fetch upstream
git switch feat/short-description
git merge upstream/main
```

解决冲突后重新运行相关检查，再 push 同一分支。优先使用普通 merge，适合当前基础；不要未经要求改写已推送分支历史。

### 法源资料库 Schema 对接方案（待评审）

本轮只做 Schema 方案对齐，未修改代码、数据库或运行配置。以下结论来自对 `apps/server/src/legal-corpus/migration.ts`、`metadata.ts`、`store.ts`、`controller.ts`、`LegalAgent_MVP_v2_Design/contracts/legal-corpus.ts`、`tools/ops/legal-corpus.ts` 和 `docs/legal-corpus.md` 的实际阅读。

**1. 法规与案例怎么建模**

- 建议继续使用同一套“资料目录 + 不可变版本”骨架，用 `corpus=law|cases` 区分法规和案例。平台侧的“案件/Matter”是用户案件，不能和公共库里的司法案例 `cases` 混用。
- `la_corpus_documents` 只保存资料身份：稳定文档 ID、`corpus`、`source_id` 和当前版本指针。
- `la_corpus_revisions` 保存一次完整来源快照：内容 hash、Blob 地址、字节数、来源元数据、采集时间。
- 法规专有字段包括公布日期、施行日期、制定机关、效力状态、文号；案例专有字段包括入库编号、案号、法院、案由、审级、裁判日期、案例分类和案例类型。当前实现使用受控 `metadata` JSONB 加 `raw` front matter，能承接两类字段，但后续若频繁按法院、案由、文号筛选，应把高频字段提升为独立列并建索引。

**2. 稳定 ID**

- 文档 ID：`lc_` + `SHA-256(corpus + ":" + source_id)`。
- 版本 ID：`lcr_` + `SHA-256(document_id + ":" + content_sha256)`。
- `source_id` 必须是官方来源内的稳定标识：法规用 `bbbs`，案例用 `case_id`。标题、文号、文件名、URL 查询参数、采集时间和正文 hash 都不能替代来源 ID。
- 当前 ID 的边界是“同一来源记录”。如果以后要合并不同官网发布的同一部法律，需要再增加一层 `work` 聚合实体；本期两个固定来源不需要提前实现。

**3. 原文与元数据**

- 原始字节继续放 BlobStore，对象键为 `legal-corpus/<corpus>/<documentId>/<sha256>.md`，对象不可变；PostgreSQL 只保存 `object_ref`、`sha256`、`byte_size`、`mime_type`、元数据和检索文本。
- Metadata 是规范化后的查询字段；原始 front matter 完整保留在 `metadata.raw`，用于追溯和以后补充字段映射。
- 原文读取必须带 `document_id + revision_id`，读回后重新校验字节数和 SHA-256，不能按“当前版本”隐式读取历史内容。
- 当前导入器只纳入 Markdown 正文和 front matter。资料包另有 44 份 DOC/PDF 附件，尚未进入 BlobStore；若这些附件要作为正式原文证据，需要新增 `la_corpus_assets`（关联 revision、角色、文件名、MIME、hash、object_ref）后再联调。

**4. 历史版本与当前版本**

- 所有 revision 永久不可变，不删除、不覆盖；同一文档同一内容 hash 只保留一个 revision。
- `current_revision_id` 只表示“公共库当前发布给平台和 Agent 的版本”，不表示“法律效力当前有效”。效力状态来自来源元数据，且仍标记为 `SOURCE_SNAPSHOT_NOT_CURRENTLY_VERIFIED`。
- 写入契约必须显式区分 `PUBLISH` 与 `BACKFILL`：`PUBLISH` 插入新 revision 后移动当前指针；`BACKFILL` 只补充历史 revision，不移动指针；已存在 hash 两者都幂等返回 `UNCHANGED`。
- 当前 `LegalCorpusStore.put()` 对“已存在 hash”不移动指针，但对“未见过的任意 hash”会直接更新当前指针。若导入旧包包含一个当前库中尚未见过的历史 hash，按源码推断仍可能回滚当前版本；在 Schema 冻结前应补上显式发布模式和回归测试，不能只依赖调用方约定。
- 当前 revision hash 覆盖整个 Markdown 文件，包含 front matter。因此 `collected_at` 或元数据变化也会形成新 revision。建议明确取舍：保留“完整来源快照”作为版本，同时增加正文 `content_sha256` 用于识别纯正文是否变化；如果只希望正文变化才新增版本，则需要把规范化元数据单独存储并建立明确规则。

**5. 采集系统写入方式**

- 不建议让采集器直接执行 SQL。数据库服务应提供唯一写入口，负责校验来源字段、内容 hash、稳定 ID、字节数、幂等键、任务状态和发布模式。
- 当前可用链路是：采集器写维护工作区，运维通过 `corpus:ops -- import/reconcile` 入队，Worker 调用 `reconcile()` 和 `LegalCorpusStore.put()`。这条链路适合同机脚本和已有全量导入，但不适合作为独立采集服务的长期 HTTP 契约。
- 建议下一步增加内部写入契约：`POST /internal/v1/legal-corpus/revisions`，要求服务身份认证和 `Idempotency-Key`。请求至少包含 `corpus`、`sourceId`、`sourceUrl`、`metadata`、`markdown`（或上传对象引用）、`sha256`、`mode=PUBLISH|BACKFILL`、`observedAt`、`collectorVersion`。数据库服务重新计算 hash，不信任客户端声明，并返回 `documentId`、`revisionId`、`result=CREATED|UNCHANGED|BACKFILLED`、`currentRevisionId`。
- 如果采集与数据库始终同机同进程，也可以先冻结内部服务方法 `LegalCorpusIngestService.publish()`，但不能再让采集器自行拼装目录表和当前指针。HTTP 契约的优点是进程、语言和部署可以分离，便于采集系统独立演进。
- 维护任务状态继续只走 `la_corpus_jobs`/`la_corpus_schedules` 或内部运维接口，不通过平台公共 API 暴露。

**6. 平台与 Agent 只读 API**

- `GET /api/v1/legal-corpus/stats`：返回法规/案例数量、revision 数量、采集时间范围和检索状态。
- `GET /api/v1/legal-corpus/documents`：按 `corpus`、效力状态、案例分类和稳定 ID 游标分页浏览当前发布版本。
- `GET /api/v1/legal-corpus/search`：关键词检索当前发布版本，返回固定 `documentId`、`revisionId`、SHA-256、来源 URL、元数据和受限片段。
- `GET /api/v1/legal-corpus/documents/{documentId}/revisions`：读取历史版本摘要。
- `GET /api/v1/legal-corpus/documents/{documentId}/revisions/{revisionId}/content`：读取固定版本原文，服务端复验 hash 和字节数。
- Agent 的 `law_search` 应复用同一个检索服务，限制 `limit<=10`，只返回固定版本、来源和片段；需要原文时再按固定 `documentId + revisionId` 读取，不让 Agent 自己拼法条或访问维护表。
- 所有读取要求登录和组织绑定；维护状态只给管理员。公共库不接收用户案件材料，也不提供平台或 Agent 写入权限。

**联调样例建议**

| 样例 | 预期 |
| --- | --- |
| 1 条法规首次 `PUBLISH` | 新建 document/revision，current 指向该版本 |
| 1 条案例首次 `PUBLISH` | 案例字段完整，`cause/court/caseNo` 可按约定筛选 |
| 同一内容重复 `PUBLISH` | `UNCHANGED`，不新增 revision |
| 已有新版后导入旧版 `BACKFILL` | 新增历史 revision，current 仍指向新版 |
| 旧版再次重放 | `UNCHANGED`，current 不变 |
| 只改 front matter 中采集时间并再次 `PUBLISH` | 明确预期：新增完整快照版本，或按正文 hash 判为 unchanged，必须在冻结前二选一 |
| 故意篡改 hash/字节数 | 拒绝写入，任务失败，不发布半成品 |
| 读取固定 revision | 返回原文并通过 SHA-256 校验 |

**待评审决策**

1. 版本去重依据采用“完整 Markdown 文件 hash”还是“正文 hash + 元数据版本”两字段。
2. 采集系统与数据库之间采用内部 HTTP 写入 API，还是继续使用维护工作区 + Worker 的内部服务方法。
3. DOC/PDF 附件是否进入本期正式资料范围。
4. 法规/案例专有字段哪些提升为独立列，哪些继续放在 JSONB。
5. `PUBLISH`/`BACKFILL` 语义及旧包回滚回归测试必须在 Schema 冻结前完成。
