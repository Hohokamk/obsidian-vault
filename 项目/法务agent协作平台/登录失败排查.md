# 登录失败排查：Better Auth Invalid Origin

## 时间
2026-10-29

## 现象

`dev`、`worker`、web 三个服务全部启动，Docker 容器正常运行，输入 `demo-credentials.json` 中的账号密码登录时，前端提示"暂时无法完成登录"。

## 排查过程

### 1. 检查基础服务状态

```bash
docker ps                    # 容器在跑
ss -tlnp | grep 3310         # API 在监听
ss -tlnp | grep 5173         # Web 在监听
ps aux | grep node           # dev + worker + vite 三个进程都在
```

三个服务均正常。

### 2. 查看 dev 服务器日志

关键报错：

```
ERROR [Better Auth]: Invalid origin: http://127.0.0.1:5173
{"route":"/api/auth/*splat","httpStatus":403}
```

## 请求链路（为什么会走到这个报错）

理解这个问题需要看清楚一次登录请求的完整路径：

```
浏览器（http://127.0.0.1:5173）
  │  用户在登录页输入账号密码，点登录
  │  前端调用: POST /api/auth/sign-in/email
  │  Origin: http://127.0.0.1:5173
  │
  ▼
Vite 开发服务器（5173 端口）
  │  vite.config.ts 里配了 proxy: { '/api': { target: 'http://127.0.0.1:3310' } }
  │  收到 /api 开头的请求 → 转发到后端
  │  转发时：方法、body、headers 都带上
  │  但 Origin 头保持原样：http://127.0.0.1:5173
  │
  ▼
后端 API 服务器（3310 端口）
  │  Express 收到请求，匹配 /api/auth/*splat 路由
  │  进入 Better Auth 的 toNodeHandler
  │
  ▼
Better Auth（auth.ts）
  │  检查 Origin: http://127.0.0.1:5173
  │  对比 trustedOrigins 列表 → 不在里面
  │  ❌ 拒绝请求，返回 403
  │
  ▼
前端收到 403 → 显示"暂时无法完成登录"
```

### 关键点：Vite proxy 不会改写 Origin 头

Vite 的 proxy 配置只转发请求体、路径和部分 headers。`Origin` 这个浏览器自动加的头不会被改写。所以后端看到的请求来源仍然是前端 dev server 的地址，而不是后端自己的地址。

### 生产环境为什么没有这个问题

生产部署时，前端是静态文件，由 Nginx/Caddy 等网关托管，前后端同源（同一个域名+端口），`Origin` 就是 `baseURL` 本身，天然在信任列表里。这个问题只出现在本地开发环境的前后端分离场景。

## 端口定义一览

| 端口 | 谁定义的 | 定义位置 | 用途 |
|------|---------|---------|------|
| 3310 | 后端 | `apps/server/src/config.ts` (`LEGALAGENT_API_PORT`) | API 服务器 |
| 5173 | 前端 | `apps/web/vite.config.ts` (Vite 默认) | Web 开发服务器 |
| 5432 | Docker | `compose.yaml` (容器内部端口) | PostgreSQL（映射到 32768） |

两个端口各写各的，没有统一配置文件。`.env.local` 里的 `AUTH_URL` 是后端告诉前端"我在哪"的唯一桥梁。

## 修复

### 改了什么

三个文件，思路是**环境变量作为单一来源**：

**1. `apps/server/src/config.ts`** — 新增 `frontendOrigin` 字段

```typescript
export interface ServerConfig {
  databaseUrl: string;
  authSecret: string;
  baseUrl: string;
  port: number;
  host?: string;
  frontendOrigin?: string;                    // 新增
  blobDirectory: string;
  ...
}

// readConfig 里加一行：
frontendOrigin: env.LEGALAGENT_FRONTEND_ORIGIN,
```

**2. `apps/server/src/auth.ts`** — 用 config 替代硬编码

```typescript
trustedOrigins: [config.baseUrl, config.frontendOrigin].filter(Boolean),
```

`filter(Boolean)` 去掉 undefined，确保数组里只有有效值。

**3. `.env.local`** — 加一行

```bash
LEGALAGENT_FRONTEND_ORIGIN='http://127.0.0.1:5173'
```

### 修改后如果你改了 Vite 端口怎么办

**是的，还是需要你手动同步修改。**

完整链路是：

```
Vite 端口变了（比如 5173 被占用了，改成 5174）
  │
  ├─ vite.config.ts: { port: 5174 }          ← 改前端
  │
  ├─ .env.local: LEGALAGENT_FRONTEND_ORIGIN='http://127.0.0.1:5174'   ← 跟着改这行
  │
  └─ 后端 auth.ts 不需要改（它读 config → 读环境变量，自动生效）
```

为什么做不到"后端自动感知前端端口"：后端和前端是两个独立进程，后端不可能提前知道前端选了哪个端口。`dev:setup` 只管理后端和数据库的初始化，不碰前端的 Vite 配置。所以这个同步只能由开发者手动维护。

**最小维护成本**：改 `.env.local` 这一行，重启 dev 服务即可。不需要碰代码。

## 正确的本地启动顺序

```bash
# 终端 1：首次或 Docker 容器停了之后必须跑
npm run dev:setup

# 终端 1
npm run dev

# 终端 2
npm run worker

# 终端 3
npm run dev --workspace @legalagent/web
```
