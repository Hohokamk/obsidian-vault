## 四、共同数据模型

当前候选实现使用两张核心表和两张维护表。

### 4.1 资料目录

`la_corpus_documents`：

| 字段 | 含义 |
| --- | --- |
| `id` | 稳定文档 ID，格式为 `lc_` 加 64 位 SHA-256 |
| `corpus` | `law` 或 `cases` |
| `source_id` | 法规使用官方 `bbbs`，案例使用官方 `case_id` |
| `current_revision_id` | 当前发布版本；补录历史时允许为空 |
| `created_at` | 目录创建时间 |

同一 `(corpus, source_id)` 只能有一条目录记录。

稳定 ID：

```text
document_id = "lc_" + SHA-256(corpus + ":" + source_id)
revision_id = "lcr_" + SHA-256(document_id + ":" + sha256)
```

### 4.2 不可变版本

`la_corpus_revisions`：

| 字段 | 含义 |
| --- | --- |
| `id` | 不可变版本 ID |
| `document_id` | 所属资料目录 |
| `sha256` | 整份 Markdown 原始字节的 SHA-256 |
| `object_ref` | BlobStore 对象地址 |
| `byte_size` | 原文字节数 |
| `metadata` | 从 front matter 映射的结构化元数据 |
| `search_text` | 去掉 front matter 后用于关键词查询的正文 |
| `imported_at` | 入库时间 |

同一 `(document_id, sha256)` 只能有一个版本。

原文对象路径当前为：

```text
legal-corpus/{corpus}/{document_id}/{sha256}.md
```

读取指定版本时必须同时校验 `byte_size` 和 `sha256`。hash 覆盖整份 Markdown，包括 front matter；只修改采集时间也可能形成新版本。

### 4.3 元数据

法规和案例共用严格对象，至少包含：

- `title`
- `sourceId`
- `sourceUrl`
- `sourceName`
- `scope`
- `validityStatus`
- `promulgationDate`
- `effectiveDate`
- `issuingAuthority`
- `collectedAt`
- `caseCategory`
- `caseType`
- `entryNumber`
- `keywords`
- `rights`
- `verification`
- `raw`

当前 `verification` 固定为：

```text
SOURCE_SNAPSHOT_NOT_CURRENTLY_VERIFIED
```

它表示“这是已入库的来源快照，不证明该资料此刻仍然有效”。平台、网页和 Agent 都必须保留这个限制。

### 4.4 维护表

- `la_corpus_jobs` 保存维护任务状态、阶段、计数、错误码和取消标志。
- `la_corpus_schedules` 保存允许定时执行的增量法律检查和案例列表检查。
- 这两张表属于采集维护边界，不通过公共只读 API 暴露原始载荷。

## 五、采集维护系统到数据库的写入契约

### 5.1 当前逻辑接口

当前候选实现的实际入口是：

```text
LegalCorpusStore.put(
  corpus,
  {
    sourceId,
    metadata,
    sha256,
    bytes
  },
  {
    jobId?,
    mode?
  }
)
```

返回：

```text
{
  documentId,
  revisionId,
  changed,
  published
}
```

当前含义：

- `mode` 默认是 `PUBLISH`。
- `PUBLISH` 新增版本后移动 `current_revision_id`。
- `BACKFILL` 只新增历史版本，不移动当前版本指针。
- 相同文档和相同 hash 再次写入时幂等返回 `changed=false`。
- 已存在版本重放时会校验原文对象；对象缺失可按已校验来源补齐，对象内容错误则失败。
- 传入 `jobId` 时，写入事务会确认该任务仍为 `RUNNING` 且未请求取消；否则返回 `CORPUS_JOB_NOT_ACTIVE`。

### 5.2 我交给数据库侧的数据

首版建议把以下内容视为一次写入的完整输入：

| 输入 | 是否必填 | 约定 |
| --- | --- | --- |
| `corpus` | 是 | 只能是 `law` 或 `cases` |
| `sourceId` | 是 | 法规 `bbbs`，案例 `case_id` |
| `bytes` | 是 | UTF-8 Markdown，包含 front matter 和原文，单文件不超过 8 MiB |
| `sha256` | 是 | 对 `bytes` 全字节计算；服务端必须重新计算，不信任调用方 |
| `metadata` | 是 | 可按当前严格对象传递，但服务端应重新解析关键字段或执行校验 |
| `mode` | 是 | `PUBLISH` 或 `BACKFILL` |
| `jobId` | 否 | 后台任务写入时携带；人工修复可省略，但要显式标识 |

文档 ID、版本 ID、对象路径和入库时间都由数据库服务生成，调用方不能自行指定。

### 5.3 首版建议的 HTTP 映射

只有在双方决定分开部署时才需要新增内部 HTTP。逻辑字段不应因改成 HTTP 而变化。

建议接口：

```text
POST /internal/legal-corpus/revisions
```

请求示例：

```json
{
  "contractVersion": "legal-corpus-write/v1",
  "corpus": "law",
  "sourceId": "official-source-id",
  "mode": "PUBLISH",
  "sha256": "64-char-lowercase-hex",
  "metadata": {},
  "contentBase64": "optional-or-use-upload-ref",
  "jobId": "lcj_optional",
  "idempotencyKey": "collector-operation-key"
}
```

建议响应：

```json
{
  "documentId": "lc_...",
  "revisionId": "lcr_...",
  "result": "PUBLISHED_NEW",
  "currentRevisionId": "lcr_..."
}
```

建议结果枚举：

- `PUBLISHED_NEW`：新增版本并成为当前版。
- `STORED_HISTORY`：新增历史版本，没有移动当前版。
- `UNCHANGED`：相同文档和 hash 已存在。

错误必须可区分：

- `VALIDATION_FAILED`
- `HASH_MISMATCH`
- `SOURCE_ID_CONFLICT`
- `IDEMPOTENCY_CONFLICT`
- `JOB_NOT_ACTIVE`
- `SOURCE_UNRESOLVED`
- `NOT_FOUND`

以上 HTTP 请求、响应和错误枚举是建议，不是当前已经冻结的公共契约。

## 六、数据库到平台和 Agent 的只读契约

当前候选接口如下：

| 方法 | 路径 | 权限 | 用途 |
| --- | --- | --- | --- |
| GET | `/api/v1/legal-corpus/stats` | 已登录且绑定机构 | 文档数、版本数、采集时间范围、检索状态 |
| GET | `/api/v1/legal-corpus/documents` | 已登录且绑定机构 | 当前版本目录、分页、效力和案例分类筛选 |
| GET | `/api/v1/legal-corpus/search` | 已登录且绑定机构 | 标题和正文关键词检索，返回固定版本和片段 |
| GET | `/api/v1/legal-corpus/documents/{documentId}/revisions` | 已登录且绑定机构 | 固定文档的历史版本 |
| GET | `/api/v1/legal-corpus/documents/{documentId}/revisions/{revisionId}/content` | 已登录且绑定机构 | 读取并校验固定版本原文 |
| GET | `/api/v1/legal-corpus/maintenance` | 机构管理员 | 有界任务状态、计数和调度，不含路径和日志 |

目录与检索结果至少返回：

```text
id, corpus, sourceId, revisionId, sha256, byteSize, metadata, importedAt
```

检索结果额外返回受限 `snippet`。它不能替代原文读取，也不能证明当前效力。

Agent `law_search` 当前输入：

```text
q: 必填，1 到 200 字
corpus: 可选，law 或 cases
limit: 1 到 10，默认 5
```

返回标题、来源 URL、效力或案例元数据、受限片段，以及固定 `documentId`、`revisionId` 和 `sha256`。模型引用时必须使用这些固定版本标识。

当前 Agent 工具直接调用服务端的 `LegalCorpusStore.search()`，不经过公共 HTTP。如果朱把数据库和读取服务独立部署，需要明确 Agent 最终是：

1. 继续共享数据库并直接使用同一查询实现；还是
2. 调用朱提供的内部只读 API。

这一点不能等 Agent 接入时再临时决定。

### 7.2 语义仍需明确

- `BACKFILL` 写入一个从未出现的文档时，当前会创建目录和历史版本，但没有 `current_revision_id`，因此不会出现在目录、检索和统计中。首版建议限制 `BACKFILL` 只用于已存在目录，或者显式定义“仅历史、不可公开读取”的状态。
- 当前 `PUBLISH` 只在新增 revision 时移动指针。把一个已知历史版本重新设为当前版、显式回滚当前版，目前没有接口。
- 当前没有删除、撤回、失效公告或 tombstone 规则。缺失文件也不会自动删除已发布资料。
- current stats 只统计具有当前版本的目录，不能把历史补录数量直接解释成可浏览资料数。
- 当前 BlobStore 写入发生在 PostgreSQL 事务前。事务失败可能留下未被引用的对象，需要约定清理策略；但未引用对象不能对外可见。

   - 我当前分支有候选实现，可以作为参考代码和测试样例，但不会把“代码已存在”当成朱侧已经交付。

8. **错误与幂等**
   - 默认：同文档同 hash 重放返回 `UNCHANGED`；相同幂等键对应不同输入返回冲突。
   - 校验失败不能改当前版本指针；任务失效不能继续发布。

## 九、联调验收用例

双方至少用同一组固定样例跑完以下用例：

| 用例 | 输入 | 预期 |
| --- | --- | --- |
| 法规首次发布 | 一份全国性法规 Markdown，`PUBLISH` | 新目录、新版本、当前指针指向该版本 |
| 案例首次发布 | 一份案例 Markdown，`PUBLISH`，`content_source=content` | 新目录、新版本、可按 `case_id` 查询 |
| 重复导入 | 相同文档和 hash 再写一次 | `UNCHANGED`，版本数不增加，当前指针不变 |
| 发布新版本 | 同文档新 hash，`PUBLISH` | 版本数加一，当前指针移动 |
| 补录旧历史 | 同文档未见过的旧 hash，`BACKFILL` | 版本数增加，当前指针不移动 |
| 非法历史补录 | 新文档直接 `BACKFILL` | 按最终协商结果返回明确错误，不能静默变成不可见数据 |
| hash 错误 | 声明 hash 与实际字节不同 | 拒绝写入，目录和版本不变 |
| 任务已取消 | `jobId` 对应任务不是 `RUNNING` | 拒绝写入并返回任务失效错误 |
| 原文对象缺失 | 已入库版本对象缺失后重放同字节 | 可恢复并重新校验成功 |
| 原文对象篡改 | 对象字节和 hash 不一致 | 返回完整性错误，不返回错误原文 |
| 读取固定版本 | 使用 `documentId + revisionId` | 返回原文并校验字节数与 hash |
| 平台检索 | 标题或正文关键词 | 返回当前发布版本、固定 ID、来源和片段 |
| Agent 检索 | 聚焦法律关键词，`limit<=10` | 返回固定版本标识，模型不获得维护状态或日志 |
| 权限边界 | 普通成员读取维护接口 | 拒绝访问 |

联调还要做一次数量对账：

- 当前资料包 `data/legal-corpus/DATA-MANIFEST.json` 的记录为 7,804 份：法规 2,224 份，案例 5,580 份。
- 上述是样例清单数量，不等于本轮数据库实际入库数。
- 全量导入后要分别核对 manifest 数量、目录数、版本数、失败数、BlobStore 对象数和平台可查询数。
