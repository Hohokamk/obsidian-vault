# 11.03 法源资料库任务清单

## 简要分析

本次把法源资料库 step0 的 12 张任务卡单独整理成一份可传递清单，覆盖公共库基线、schema、样例数据、只读接口、三个已知 bug、采集维护前端、平台检索和 Agent tool。每张卡都写明分支、目标、输入、要做、不要做、交付物和验收，可以直接单独交给一个人执行。当前最重要的前置动作是先在 `feature/legal-corpus-db` 合并 `origin/husky`，再开始其他开发。

## 任务卡 01：建立公共法源资料库基线

- **分支**：`feature/legal-corpus-db`
- **目标**：把最新 `main` 与 `origin/husky` 初版合成一个可开发的公共库基线。
- **输入**：最新 `main`、`origin/husky` 分支、`docs/legal-corpus.md`、`apps/server/src/legal-corpus/`。
- **要做**：
  1. 切到 `feature/legal-corpus-db`。
  2. 合并 `origin/husky`。
  3. 确认合并结果能构建、类型检查通过。
  4. 不做业务重构，只建立基线。
- **不要做**：
  - 不直接改 `main`。
  - 不把 `AGENTS.md`、`PROJECT_ONBOARDING.md` 混入业务提交。
- **交付物**：一个包含初版法源库代码的 `feature/legal-corpus-db` 分支。
- **验收**：`git merge --no-ff origin/husky` 成功，`npm run typecheck --workspace @legalagent/server` 通过。

## 任务卡 02：确认公共库 schema

- **分支**：`feature/legal-corpus-db`
- **目标**：确定公共法源资料库的数据模型。
- **输入**：`apps/server/src/legal-corpus/migration.ts`、`store.ts`、`metadata.ts`、黄圣乔现有数据、朱皓宇的 schema 意见。
- **要做**：
  1. 明确 `corpus`、`source_id`、`document_id`、`revision_id` 的含义。
  2. 确认稳定 ID 生成规则。
  3. 确认版本不可变规则。
  4. 确认元数据字段：来源、效力、日期、机关、分类、采集时间。
  5. 确认只读查询接口和写入边界。
- **不要做**：
  - 不把案件、机构、用户私有材料混进公共库。
  - 不让平台或 Agent 直接写公共库。
- **交付物**：schema 设计说明和迁移代码。
- **验收**：`LEGAL_CORPUS_MIGRATION` 能在隔离数据库执行，字段与样例数据匹配。

## 任务卡 03：导入最小样例数据

- **分支**：`feature/legal-corpus-db`
- **目标**：先让公共库有可查询、可预览的真实样例。
- **输入**：`origin/husky` 的 `data/legal-corpus`、`DATA-MANIFEST.json`、`workspace/law`、`workspace/cases`。
- **要做**：
  1. 选一小批法律和案例。
  2. 校验 hash、路径和元数据。
  3. 导入到隔离数据库。
  4. 确认能通过 API 查询和预览。
- **不要做**：
  - 不一次性导入全量数据。
  - 不把失败数据伪装成成功。
- **交付物**：可复现的导入命令和样例数据。
- **验收**：`npm run corpus:ops -- import`、`once`、`status` 能跑通，查询结果不为空。

## 任务卡 04：公共库只读查询接口

- **分支**：`feature/legal-corpus-db`
- **目标**：给平台和 Agent 提供稳定、只读的查询能力。
- **输入**：`apps/server/src/legal-corpus/controller.ts`、`store.ts`、`@legalagent/contracts/api`。
- **要做**：
  1. 保留或完善 stats、documents、revisions、content 接口。
  2. 确保所有查询都走 SQL 过滤。
  3. 确保返回固定版本和元数据。
  4. 确保匿名或失效会话被拒绝。
- **不要做**：
  - 不暴露采集任务内部状态。
  - 不提供写入接口。
  - 不把未实现的搜索说成已实现。
- **交付物**：只读 API 和契约测试。
- **验收**：`apps/server/test/legal-corpus.test.ts` 中 HTTP 目录、版本、内容、权限测试全部通过。

## 任务卡 05：修复导入旧包回滚当前版本

- **分支**：`feature/legal-corpus-db`
- **目标**：导入历史包不能把当前版本指针回滚到旧版。
- **输入**：`apps/server/src/legal-corpus/importer.ts`、`store.ts`。
- **要做**：
  1. 区分“补录历史版本”和“发布当前版本”。
  2. 重复导入旧 hash 时不更新 `current_revision_id`。
  3. 只有新版本发布才更新当前指针。
  4. 补一个旧包重放的回归测试。
- **不要做**：
  - 不用时间戳判断新旧。
  - 不删除历史版本。
- **交付物**：修复后的 store/importer 逻辑和测试。
- **验收**：测试覆盖“当前为新版，导入旧包，当前仍指向新版”。

## 任务卡 06：拆分采集维护系统边界

- **分支**：`feature/legal-corpus-maintenance`
- **目标**：采集维护不依赖 main 业务应用初始化。
- **输入**：`apps/server/src/legal-corpus/maintenance/`、`tools/legal-corpus/`、`apps/server/src/bootstrap.ts`。
- **要做**：
  1. 从 `feature/legal-corpus-db` 合并最新基线。
  2. 把采集任务、Worker、采集器和公共库写入接口独立成边界。
  3. 保留运维入口，不暴露给普通用户和 Agent。
  4. 明确采集系统只通过公共库发布校验后的版本。
- **不要做**：
  - 不让采集代码直接读案件或机构数据。
  - 不把采集按钮放进用户页面。
- **交付物**：独立维护模块和边界说明。
- **验收**：采集 Worker 能独立启动，任务能写入公共库，业务 API 不依赖采集进程存活。

## 任务卡 07：修复失败重试跳过失败项

- **分支**：`feature/legal-corpus-maintenance`
- **目标**：显式重试必须消费失败队列，而不是重新入队原参数后跳过失败项。
- **输入**：`tools/legal-corpus/collectors/case_maintenance_backend.py`、`maintenance/jobs.ts`。
- **要做**：
  1. 给重试任务加明确模式。
  2. 让重试只处理失败记录。
  3. 记录新增、成功、失败数量。
  4. 补一个“首次失败，重试后重新请求详情”的测试。
- **不要做**：
  - 不把失败状态直接改成成功。
  - 不静默跳过失败项。
- **交付物**：重试逻辑和回归测试。
- **验收**：测试中重试必须发出详情请求，新增或恢复数量不为零且状态真实。

## 任务卡 08：修复取消和超时进程树终止

- **分支**：`feature/legal-corpus-maintenance`
- **目标**：取消或超时后完整终止采集进程树，释放锁和队列。
- **输入**：`apps/server/src/legal-corpus/maintenance/collector.ts`。
- **要做**：
  1. Windows 继续使用进程树终止。
  2. Linux 补齐子进程树终止。
  3. 加有界等待和强制终止兜底。
  4. 确认输出管道关闭、锁释放。
  5. 补超时和取消测试。
- **不要做**：
  - 不只杀父进程。
  - 不无限等待后代退出。
- **交付物**：进程管理修复和测试。
- **验收**：超时或取消后，后代进程不再继续写入，Worker 能在限定时间内返回。

## 任务卡 09：维护系统简单前端

- **分支**：`feature/legal-corpus-maintenance`
- **目标**：给运维人员一个能判断采集健康度的简单页面。
- **输入**：`la_corpus_jobs`、`la_corpus_documents`、`la_corpus_revisions`、现有平台 UI 风格。
- **要做**：
  1. 展示任务状态、进度、失败原因。
  2. 展示资料数量和最近导入时间。
  3. 支持失败项简易预览。
  4. 只允许运维访问，不给普通用户入口。
- **不要做**：
  - 不做复杂图表。
  - 不把原始诊断日志暴露给普通用户。
  - 不提供普通用户触发采集的按钮。
- **交付物**：维护状态页面和权限边界。
- **验收**：能看到任务状态、数据量和失败队列，且未授权用户无法访问。

## 任务卡 10：平台法律法规检索框

- **分支**：`feature/legal-corpus-platform`
- **目标**：在现有法律检索页面里加入专门的法律法规检索。
- **输入**：`apps/web/src/modules/legal-corpus/CorpusLibrary.tsx`、现有法律检索页面、公共库只读 API。
- **要做**：
  1. 从 `feature/legal-corpus-db` 合并最新基线。
  2. 添加法律法规检索框。
  3. 展示结果列表、元数据和固定版本。
  4. 支持预览原文。
  5. 保持与现有平台 UI 风格一致。
- **不要做**：
  - 不直接查采集任务状态。
  - 不显示未实现的搜索能力。
- **交付物**：检索页面和预览组件。
- **验收**：页面能按关键词检索法律法规，预览能打开固定版本。

## 任务卡 11：Agent 检索 tool

- **分支**：`feature/legal-corpus-platform`
- **目标**：让文书起草等 Agent 进程能调用法律法规检索并拿到结果。
- **输入**：公共库只读接口、现有 Agent 工具注册方式、Mastra runtime。
- **要做**：
  1. 定义 tool 输入、输出和错误。
  2. 接入公共库查询。
  3. 确保结果带来源、版本和元数据。
  4. 在文书起草 Agent 中实际调用一次。
  5. 补 Agent 调用链路测试。
- **不要做**：
  - 不让 Agent 触发采集。
  - 不返回无来源的伪造法条。
- **交付物**：可调用的法律检索 tool。
- **验收**：Agent 进程能通过 tool 获得真实检索结果，并且结果可追溯到固定版本。

## 任务卡 12：端到端验证与交付

- **分支**：三个功能分支最后都要覆盖
- **目标**：证明从采集到展示的整条链路真实可用。
- **输入**：三个分支的最新代码、隔离数据库、样例数据、Playwright。
- **要做**：
  1. 跑公共库 API 测试。
  2. 跑采集任务恢复、取消、超时、重试测试。
  3. 跑平台页面和 Agent tool 测试。
  4. 用浏览器做一次完整预览。
  5. 记录已验证和未验证边界。
- **不要做**：
  - 不把类型检查当作端到端验证。
  - 不把“服务启动”当作“业务可用”。
- **交付物**：测试报告和交付说明。
- **验收**：`npm run typecheck --workspace @legalagent/server`、`npm run typecheck:web`、`node --import tsx --test apps/server/test/legal-corpus.test.ts`、`npm run test:e2e` 中相关用例通过。
