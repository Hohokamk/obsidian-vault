# 法源任务收尾方案

## 简要分析

本次按 11.03 任务清单的 12 张卡逐条核对当前仓库真实状态，确认核心功能与三个 bug 修复基本到位，但交付形态与原始分支方案不符，且"全部完成并做好测试"尚不能成立。核对中发现两个新问题：队友分支 `origin/feature/legal-corpus-ui-agent` 的 CI 中 `Minimal runtime` 为红色（4 个测试失败），其提交把只读案件助手链路挂上了 `law_search` 工具并硬编码了数据库连接串；本地 `codex/legal-corpus-integration` 已把这个红色提交合了进来（未推送）。当务之急是先修回归、再按"数据库基线分支 -> 维护/平台两条长期分支"归位分支结构，然后补真实模型调用、真实上游采集和双方联调三项"真实"证据。

## 现状核对（已实际验证）

分支与提交（`git log --graph --all`、`git rev-parse`）：

- `feature/legal-corpus-db` = `bcf12b6b`，已推送，PR #42（-> `main`）OPEN、MERGEABLE，6 项检查（Contracts、Design documentation、Minimal runtime x2、Web and browser x2）全部 SUCCESS（11-05）。
- `origin/feature/legal-corpus-ui-agent` = `3ba3c85d`（朱皓宇，11-05 20:31），与 `feature/legal-corpus-db` 从同一点 `5a907926` 分叉；CI 只有 `Web and browser` 成功，`Minimal runtime` 失败。
- 本地 `codex/legal-corpus-integration` = `bcf12b6b` 合入 `3ba3c85d` 的合并提交 `d4631735`，未推送；分支名用了 `codex/` 前缀（本人此前明确反对过该命名）。
- 本地 `feature/legal-corpus-maintenance`、`feature/legal-corpus-platform` 均停在 `3f127c42`（旧 main），是从未推进的空壳，不承载任何工作。

`Minimal runtime` 失败的 4 个测试（run 42028660352，856 过 4 败）：

1. `apps/server/test/b11-organization-admin.test.ts`：`a stored credential, not the environment, is the target gateways compare` 与 `revocation disables the next run instead of resurrecting the environment`。根因：队友把 `apps/server/src/organization-admin/model-source.ts` 的 `environment()` 改成要求 `config.apiKey` 存在才返回环境配置，而测试里的环境回退配置没有 api key，"从未存凭据的机构回退到环境配置"这条既定行为被破坏，`load()` 抛 `MODEL_NOT_CONFIGURED`。
2. `apps/server/test/readonly-assistant.test.ts`：`read-only chat ... and no tools`。根因：队友在 `apps/server/src/adapters/mastra-assistant.ts` 给只读案件助手挂了 `law_search`，`toolChoice` 从 `none` 改 `auto`、`maxSteps` 从 1 改 3，测试断言"助手请求不带 tools、tool_choice 为 none"失败。

同一提交的其他问题（读 diff 确认）：硬编码数据库连接串（含口令，端口 15432，与项目实际库不一致）；每次请求 `new Pool` 不释放；BlobStore 用 `{} as any` 顶替；调用上限逻辑出现双重自增；`App.tsx` 只删了行尾换行；`.gitignore` 重复忽略 `.env.local`。

环境缺口（已实际验证）：`.local/corpus-python` 不存在，采集器 Python 环境未建；`.env.local` 只有 `DATABASE_URL`，没有 `LEGALAGENT_MODEL_*` 和 `LEGALAGENT_CORPUS_*`，与 11.10 技术日志记录的"模型能力 NOT_CONFIGURED"一致。

任务卡对照（依据 11.03 任务清单与代码现状）：卡 01-05 完成（PR #42）；卡 06-09 代码完成但真实采集运行证据缺失；卡 10 完成；卡 11 离线与挂载完成、真实模型调用未完成；卡 12 部分完成（法源单测 11/11、Web 4/4、E2E 3/3、CI 6/6 均为 fixture/离线口径）。

## 未完成项与做法

### P0 先修队友提交的回归（最高优先）

在把任何集成分支推送或合并前完成，负责人：本人修复或退给队友改，验收以 CI 为准。

1. `apps/server/src/adapters/mastra-assistant.ts`：恢复只读助手链路原状——不挂 tools、`toolChoice: 'none'`、`maxSteps: 1`、单次调用上限、原 system prompt。法源检索只走任务 Run 链路（`apps/server/src/adapters/mastra-model.ts` 的 `corpusTools` 与 `apps/server/src/adapters/legal-corpus-search-tool.ts`，已在 db 分支就位）。如果产品要求"案件助手也能检索法源"，属于设计变更：先评估隐私外发 dataClass 与调用预算，改 `apps/server/test/readonly-assistant.test.ts` 的约束并补测试，不能靠绕过测试挂载。
2. `apps/server/src/organization-admin/model-source.ts`：回退 `environment()` 改动，恢复"无库内凭据时环境配置即合法回退且不要求 apiKey"。真实模型统一走机构管理员凭据（`la_model_credentials`）；如确需 DeepSeek 环境回退，在配置层显式支持并补测试，不硬编码 provider。
3. 删除硬编码连接串：助手链路不自建 `Pool`，corpus store 由组合根注入（`apps/server/src/bootstrap.ts` 现有先例），连接串从 `LEGALAGENT_CORPUS_DATABASE_URL` 或 `DATABASE_URL` 读取；顺带修每次请求建 Pool 的泄漏。
4. 验收：`npm test --workspace @legalagent/server`（约 856 个测试）全绿，推送后 CI 6/6 全绿。

### P1 分支结构归位（交付形式）

采用"不重写历史、从当前 tip 分叉"的低风险方案：

1. `feature/legal-corpus-db` 定位为公共库基线分支（卡 01-05），PR #42 维持现状先合或先评审。
2. 从 db tip（P0 修复后的新提交）拉两条长期分支：`feature/legal-corpus-maintenance`（卡 06-09 后续）与 `feature/legal-corpus-platform`（卡 10-11 后续），把现有两条空壳分支重置到该点。
3. 队友的 UI/Agent 改动经 P0 修复后整理进 `feature/legal-corpus-platform`，请队友后续推这条；`origin/feature/legal-corpus-ui-agent` 完成后关闭。
4. 本地 `codex/legal-corpus-integration` 不推送、改名或废弃，避免 `codex/` 命名；如确需集成验证，临时建 `feature/legal-corpus-e2e`（卡 12 用），验完即删。

### P2 真实模型调用（卡 11 的"真实"部分）

1. 配一个机构模型凭据走管理员录入流程；本地冒烟可用 `LEGALAGENT_MODEL_*` 指向 fixture 或 DeepSeek，但验收证据必须来自真实 provider 的一次完整 Run。
2. 跑一次带法源问题的文书起草任务，确认 `law_search` 被真实调用，记录 `documentId/revisionId/sha256`、`callLimit` 计数与请求响应摘要（脱敏）。
3. 日志中明确区分"离线替身测试通过"与"真实模型调用通过"。

### P3 真实上游采集（卡 06-08 的"真实"部分）

1. 按 `docs/legal-corpus.md` 建环境：`python -m venv .local/corpus-python`、安装 `tools/legal-corpus/requirements.txt`、`playwright install chromium`。
2. `npm run corpus:ops -- doctor` 通过后执行 `login`（官方站点个人账号，凭据不记录），先跑一个小批量 `once`。
3. 核对 `la_corpus_jobs` 计数、失败队列、`la_corpus_documents` 新增；再真实验证一次取消/超时的进程树终止（卡 08）。
4. 风险：官方站点反爬与登录态失效；先小批量，不直接全量。

### P4 端到端与联调（卡 12 与 11.04 第九节）

1. 已有 fixture 口径：E2E 3/3、法源单测 11/11、Web 4/4。
2. 按 11.04 对接文档第九节的 14 条联调用例，用同一组固定样例逐条补真实链路：法规首发、案例首发、重复导入、新版本发布、BACKFILL 不移动指针、非法 BACKFILL、hash 错误、任务取消拒绝写入、对象缺失恢复、对象篡改拒绝、固定版本读取、平台检索、Agent 检索、权限边界。
3. 数量对账：manifest 7,804 份 vs 目录数、版本数、BlobStore 对象数、平台可查询数（11.10 技术日志已核 7,804 文档在库，还差版本数与对象数）。

### P5 交付收口

1. PR #42 合并前确认 CI 6/6 与 review 通过；队友分支修复后单独提 PR，不把红提交并进集成分支。
2. 更新交付说明：三个分支各自范围、已验证与未验证边界、联调证据位置。

## 决策与后续

执行顺序：P0（止血，约半天）-> P1（分支归位，约半天）-> P4（联调用例，与队友协同）-> P2、P3（都依赖外部凭据，可并行推进）-> P5（收口）。
