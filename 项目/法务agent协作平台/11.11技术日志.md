# 技术日志

## 简要分析

本次对 11-05 至 11-11 的法源协作工作做收尾评估，并按评估结论落地三项修复：回退 `model-source.ts` 的机构模型配置回归、删除测试文件里的残留语句、为法源检索排序补一条回归测试。已实际验证：`model-source` 修复后 b11 由红转绿（12/12），本次涉及的三个测试文件 70/70 通过，检索排序修复在 SQL 层被 A/B 对照证明有效、新测试被证明能抓住旧行为。最大风险是工作区正被另一个会话并行修改（Claude Code，12:52 启动，已切出新分支 `feature/corpus-snapshot-huggingface` 并提交），我的改动与对方的未提交改动混在同一棵树里，提交前必须先分清归属。

## 架构与代码

**1. 机构模型配置回退（本次修改）** — `apps/server/src/organization-admin/model-source.ts`

`environment()` 恢复到 main 的语义：`try { return readModelConfiguration(this.env); } catch { return undefined; }`，同时删掉两处队友提交带入的东西：`config.apiKey` 存在才返回环境配置的门槛，以及 `process.env.DEEPSEEK_API_KEY` 命中后硬编码返回 deepseek/deepseek-chat/api.deepseek.com 的回退。

理由：硬编码回退会凭空造一个不在外发白名单里的端点（返回对象没有 `allowedTargets`），`apiKey` 门槛则破坏“从未存过凭据的机构才回退环境配置、一旦 revocation 就禁用 AI”的既定行为。这是 [[11.10法源任务收尾方案]] P0 第 2 条，此前一直没做，是集成分支无法推送的直接阻塞点。

**2. 测试文件残留语句（本次修改）** — `apps/server/test/readonly-assistant.test.ts`

删掉文件末尾（最后一个 `test(...)` 之后）多出来的 `  let step = 0;`。它能过类型检查但属于编辑残留。

**3. 检索排序回归测试（本次修改）** — `apps/server/test/legal-corpus.test.ts`

新增子测试 `search ranks the shorter, more specific title ahead of longer titles that only contain the term`：造三篇标题长度不同的法条（`合成测试法` / `合成测试法司法适用解释` / `关于合成测试法的若干规定`），断言短标题排在长标题之前，且 `limit=1` 时首条是法条本体而不是更长的标题。放在 HTTP 子测试之后、standalone 子测试之前（后者在本机必挂，见“问题与排查”）。此前排序改动（`store.ts` 的 `length(r.metadata->>'title')`  Tie-break）零测试覆盖。

**4. 未改动的既有工作区改动（11-10 21:42 留到今天）**：`host-api-tool.ts`（新工具）、`mastra-model.ts`（挂载与 instructions）、`mastra-assistant.ts`（去掉硬编码连接串与 Pool 泄漏、按部署注入 `law_search`）、`bootstrap.ts`（组合根注入语料库）、`.env.example`、`model.test.ts`、`host-api-tool.test.ts`。

## 配置与部署

**新建独立测试库（本次）**：项目 Postgres 容器内建 `legalagent_test` 并启用 `pg_trgm`。DB 测试自己建/删 schema，只要指向一个专用库即可，不用另起容器。

```powershell
# 从 .env.local 的 DATABASE_URL 派生测试库连接串（口令不落盘、不记录）
$u = [Uri]((Select-String -Path .env.local -Pattern '^DATABASE_URL=').Line -replace "^DATABASE_URL='?" -replace "'?$")
$env:LEGALAGENT_TEST_DATABASE_URL = "postgresql://$($u.UserInfo)@$($u.Host):$($u.Port)/legalagent_test"
```

建库后本地可跑测试数从 736 涨到 870，此前 62 处“缺独立测试库”的失败全部转为真实执行。

**排序验证脚本（本次）**：`.local/ranking-check.mts`，独立建 schema、灌三篇法条、打印 `store.search` 的顺序与 `limit=1` 首条，用于在不跑整套 corpus 测试的情况下验证排序行为。

**临时文件处理（本次）**：`apps/server/test/` 目录下删除文件被策略拒绝，对照用的 `_head-legal-corpus.test.ts`、`_head-plus-rank.test.ts` 已移到 `.local/`（`.gitignore` 覆盖），避免被 `test/*.test.ts` glob 选中。

**环境观察**：Docker Desktop 在开机项里，但设置 `AutoStart=False`；项目 PG 宿主端口本次已从 32768 漂到 32769（`.env.local` 被同步改过才能连上）。随机端口 + 不保证自启，是会以同一姿势复发的故障源。

## 问题与排查

**1. 本地全套测试为什么红**：不带测试库时 736 个测试 90 败；带上测试库后 870 个测试 50 败，剩余失败全部是环境原因，无一是代码回归：

- Windows 无 `SeCreateSymbolicLinkPrivilege`（当前令牌 Medium Mandatory Level，实测建符号链接 `UnauthorizedAccessException`），涉及 workspace-janitor、failed-output-archive、feature-builtins、workspace 等约 32 处 EPERM；
- 子进程信号语义差异：SIGINT/SIGTERM/SIGKILL 系列在 Windows 上表现不同；
- moot-court 编译计数 438 ≠ 384（编译器/换行差异）；
- 以上需要在管理员 PowerShell 或开启开发者模式后复跑，本次未做。

**2. `legal-corpus.test.ts` 的 HTTP 子测试在本机稳定挂起**：工作区版每次都在 `HTTP catalogue/search validates schemas and permissions` 挂 118s，父测试 120s 超时后把后续子测试全部取消（包括我的新子测试）。对照实验：

| 版本 | 结果 |
| --- | --- |
| HEAD 版文件 | 4.4s 全绿，standalone 子测试仅 2.1s |
| HEAD + 仅我的排序子测试 | 12/12 通过，4.5s |
| 工作区版（含检索过滤相关改动） | HTTP 子测试必挂 118s |

结论：挂起源于工作区里另一批“检索过滤”相关改动（`store.ts` 的 validityStatus/caseCategory 过滤 + 测试里的 catalogue filters 子测试与 HTTP 过滤断言），不是我的改动；standalone 子测试变慢也是同一原因。该归属待并行会话确认。

**3. 排序修复的判别力验证**（`.local/ranking-check.mts`，三回合同一份数据、只改 SQL）：

- 带 `length(title)` Tie-break：`["合成测试法","合成测试法司法适用解释","关于合成测试法的若干规定"]`，`limit=1` 首条 `合成测试法`；
- 改回 `imported_at DESC`：顺序变成 `["合成测试法司法适用解释","合成测试法","关于合成测试法的若干规定"]`，首条 `合成测试法司法适用解释` —— 正是新测试断言的回归形态；
- 恢复后复跑一致。

过程中纠正过自己的一个错误：脚本最初按“期望顺序”灌数据，旧排序也会得到正确结果，等于没有判别力；改成按相反顺序灌数据后才成立。

**4. 并行会话（本次最重要的发现）**：`git reflog` 显示本次会话期间 HEAD 被切到 `feature/corpus-snapshot-huggingface` 并产生提交 `41f49b5a`（法源快照正文迁出 Git 改由 HuggingFace 托管）；进程列表有 3 个 `claude` 进程（12:52 启动，19:29 仍在跑测试）；工作区新增 contracts 产物、`worker.ts`、`CorpusLibrary.tsx`、docs、采集器与 3 个新测试文件的改动。我的三个文件与对方无重叠，但同树并行提交会把对方的半成品卷进我的提交，因此本次没有提交。

## 决策与后续

**已定决策**

1. 环境回退不允许硬编码 provider：无库内凭据时环境配置即合法回退，不要求 apiKey，不引入 DEEPSEEK_API_KEY 旁路。
2. 回归测试的数据构造必须让“旧行为”产生不同结果，否则没有判别力（本次自己踩到并纠正）。

**待确认**

3. 只读案件助手挂 `law_search` 属于改动设计约束（原约束是单次调用、无工具）。当前实现有界（`maxCalls=6`、每次发送前跑 egress 断言、提示词同步改写），但工具结果作为 tool 消息进入下一步 prompt 时，助手链路只断言了 `USER_PROMPT` 与固定材料的数据类别，没有对工具结果单独断言 dataClass；Run 链路有对应约束。需要产品/隐私口径确认后补决策记录。

**后续事项**

1. 与并行会话协调后再提交；建议我的三项修复单独成提交，落到 `feature/corpus-assistant-tools` 或并入 `feature/legal-corpus-platform`，不要混进 `feature/corpus-snapshot-huggingface`。
2. 修 `legal-corpus.test.ts` 工作区版的 HTTP 子测试挂起（归属并行会话）。
3. 符号链接类测试在管理员 PowerShell 下复跑一轮，确认只剩信号类环境差异。
4. 真实模型调用与真实上游采集仍是零证据，汇报时不能声称。
5. 建议固定 `LEGALAGENT_PG_PORT` 并确认 Docker Desktop 自启，避免 503 复发。
