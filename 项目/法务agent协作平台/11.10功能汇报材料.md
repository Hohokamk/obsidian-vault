三条边界都要能说出口：

1. **写入只有一条路**：只有导入器、维护 Worker 和运维命令能写资料库；平台 HTTP 和 Agent 全是只读。
2. **采集和维护不靠业务应用**：维护系统有自己的入口、自己的配置、自己的进程，不需要 API 鉴权、Better Auth、案件、材料或模型配置。
3. **资料库不认用户私有数据**：只接收两个固定官方来源的正式资料，案件私有材料走完全另一条链。

## 三、每个部分实际做了什么

### 2. 公共法源资料库

- 四张表：`la_corpus_documents`（目录）、`la_corpus_revisions`（不可变版本）、`la_corpus_jobs`（维护任务）、`la_corpus_schedules`（维护调度）。DDL 在 `apps/server/src/legal-corpus/migration.ts`，契约文档 `docs/legal-corpus-contract-v1.md` 已于 11-05 冻结。
- ID 由服务端算，调用方不能指定：`documentId = lc_ + SHA-256(corpus:sourceId)`，`revisionId = lcr_ + SHA-256(documentId:sha256)`。同一份资料重复导入、换机器重建库，ID 都不变。
- 原文一个字节不改，存 BlobStore；数据库只存目录、版本、指纹、元数据和检索文本。读取时重新校验字节数和 SHA-256。
- 写入必须显式声明 `PUBLISH` 或 `BACKFILL`，没有“覆盖”这个选项，schema 层面就拒绝 `OVERWRITE`。
- 数据规模：法律法规 2224 份、人民法院案例库案例 5580 份，合计 7804 份、7804 个版本。

### 1. 采集维护系统

- **独立进程**：`npm run corpus:ops` 和 `npm run corpus:worker` 走独立的 corpus 组合根（`composition.ts` 的 `readLegalCorpusConfig`），源码注释写得很直白：刻意不要求 API 鉴权、Better Auth、案件、材料或模型配置。这一条就是“采集维护必须通过整个业务应用初始化”的解药。
- **六类采集任务**：法律增量核验 `LAW_UPDATES`、法律元数据扫描 `LAW_SCAN`、法律失败重试 `LAW_RETRY`、案例列表核验 `CASE_CHECK`、案例详情补齐 `CASE_FETCH`、案例失败重试 `CASE_RETRY`。案例详情每批限制 1—20 条，不沿用上游的 1000 上限。
- **任务机制**：PostgreSQL 会话锁跨进程串行领取，两个 Worker 不会抢同一个任务；取消运行中的任务会终止整个采集进程树；进程异常退出后遗留任务标记为 `INTERRUPTED`，不自动重放网络动作，由运维显式重试；登录失效记为 `AUTH_REQUIRED`，定时任务不自动重试这类采集。
- **调度**：配置持久化在数据库，默认不自动联网，最短间隔一小时，只允许 `LAW_UPDATES` 和 `CASE_CHECK` 两类定时。
- **运维命令**：`migrate`、`import`、`enqueue`、`once`、`reconcile`、`status`、`jobs`、`job`、`retry`、`cancel`、`schedule`、`schedules`、`login`、`doctor`、`health`。
- **前端**：组织管理里的「法源维护」页，用平台同一套 Ant Design 组件，只读，展示资料数、任务状态、阶段、失败摘要和调度；页面上没有任何采集按钮。
- **采集器来源**：Python 采集器来自上游开源项目 Legal Auto Research（MIT），`UPSTREAM.json` 记录了四个文件的原始哈希和唯一一处本地改动及原因；没有复制对方的登录 Cookie、密钥或 profile。

### 3. 平台检索与展示模块

- 网页「律所知识库 → 法律与案例库」：检索框 + 资料类型 + 效力状态或案例分类筛选 + 分页 + 原文抽屉。抽屉里给出来源网址、使用范围、版本 SHA-256、历史版本下拉和原文目录。
- 只读 HTTP 接口五个：`stats`、`documents`、`search`、`revisions`、`revisions/:id/content`，全部要求有效登录和机构绑定；目录用稳定 ID 游标分页，筛选发生在 SQL 里。
- Agent 工具 `law_search`：输入关键词、语料类型和有界数量，返回标题、来源、效力或案例元数据、有界片段，以及固定的 `documentId`/`revisionId`/`sha256`；拿不到 front matter、文件路径、采集日志或凭据，也不能触发采集。

## 四、附 1 三个 bug 怎么修的

这是本次重构最值得讲的一段，建议单独留 5 分钟。

| # | 级别 | 原现象 | 根因 | 修法 |
| --- | --- | --- | --- | --- |
| 1 | P1 | 导入旧数据包会把当前资料回滚到旧版，磁盘是新版、数据库指针却指向旧版 | 把“第一次见到这个 hash”等同于“应该成为当前版本” | 写入显式分 `PUBLISH`/`BACKFILL`；`BACKFILL` 要求文档已有当前版本，否则报 `BACKFILL_REQUIRES_PUBLISHED_DOCUMENT`；只有 `PUBLISH` 能移动当前指针 |
| 2 | P2 | 案例采集失败后重试，可能跳过失败项还报告成功 | 采集器看到失败记录就跳过，而任务重试只是把原参数重新入队，没开失败重试模式 | 新增 `CASE_RETRY`/`LAW_RETRY`，映射到采集器 `--retry-failures`，显式消费失败队列并发起完整详情请求；跳过逻辑加上“仅在非重试模式”的判断 |
| 3 | P2 | Linux 下取消或超时不能完整终止采集进程树，Worker 继续等、维护锁不释放 | 只给 Python 父进程发 SIGTERM，没处理后代进程，也没有强杀兜底和等待上限 | 新增 `terminateProcessTree`：Windows 用 `taskkill /T /F`，POSIX 用 `ps` 枚举进程树，先 SIGTERM 后 SIGKILL，每步都有界等待；日志管道排空后才允许退出 |

三个 bug 的对应测试（今天都跑过）：

1. `reconciliation preserves history and only PUBLISH moves the current head`：验证只有 PUBLISH 能移动当前指针、历史版本保留；`BACKFILL` 遇到没有当前版本的文档直接抛错。
2. `test_first_failure_is_retried_with_a_full_detail_request`：验证第一次失败的条目在重试模式下会真的发出完整详情请求。
3. `running cancellation aborts the collector and releases the lock` 与 `cross-worker lock, cancellation and interrupted job recovery`：验证取消能中断采集并释放锁，跨 Worker 不会重复领任务。

## 九、可能被问到的问题

**Q：拆成三部分，改动量大吗？**
A：核心是划边界而不是重写。资料库的 store 和 schema 是共享地基，采集维护改成独立组合根和独立入口，平台侧只留只读接口和页面。加起来是数据库 branch 上 10 个提交加 UI/Agent 分支几个提交。

**Q：怎么保证拆开之后采集不会污染业务库？**
A：两层。配置层，维护进程只读资料库连接和存储配置，拿不到业务应用的其他配置；权限层，写入路径只有导入器、维护 Worker 和运维命令，平台 HTTP 与 Agent 只读，接口上就没有写操作。

**Q：稳定 ID 有什么用？**
A：同一份资料重复导入、换机器重建库，ID 都一样，引用不会失效；版本 ID 里含内容指纹，引用直接定位到“那一版字节”。

**Q：重复导入会怎样？**
A：同来源、同内容指纹判定为未变化，直接跳过。跑出来的结果是 `seen 7804 / added 0 / unchanged 7804`。

**Q：资料会不会过期？**
A：会，所以接口显式返回“快照当前未经核验”，页面顶部也写明效力状态以采集记录为准。更新靠运维跑增量采集并发布新版本，历史版本永远保留。

**Q：测试真的覆盖那三个 bug 吗？**

**Q：为什么不用现成的搜索引擎？**
A：当前规模 7804 份，PostgreSQL 关键词检索够用，且不引入额外组件；契约明确不冻结检索相关性，将来换 FTS5 或外部检索只影响第 2 部分的读取实现，不动数据模型。

**Q：助手也能检索法源，和任务里的工具有什么区别？**
