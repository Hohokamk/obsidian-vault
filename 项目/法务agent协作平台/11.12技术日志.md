（23:50 补充）用户问“为什么登录完之后任务状态还是显示需要登录”。查下来登录**根本没有完成**：采集器 profile 的 cookie 库里只有 2 条 cookie，其中唯一一条案例库域名的是 `Hm_lvt_...`（百度统计），没有任何登录态；任务日志里采集器拿到的响应是 `search failed: not logged in or cookie expired (code=401, msg=未登录)`。原因也清楚了：案例库**首页在未登录时看起来完全能用**（有检索框、有分类），而“登录”只是右上角一个不起眼的文字链接，点进去会跳到另一个域名的统一认证页 `account.court.gov.cn`（手机号 + 密码 + 协议勾选）。在首页扫一眼就关窗，profile 里什么都不会留下。已把登录窗口改成会自己判断：用**采集器自己的检索接口**（`/cpws_al_api/api/cpwsAl/search`，一页空检索）实时探测，结论以常驻提示条显示在窗口底部——橙色“尚未登录，请点右上角登录”，绿色“登录成功，可以关闭窗口”；在统一认证页上不发起探测（同源请求会 CORS 失败），改为提示“正在统一认证页面登录”。实测：窗口打开后立刻正确报出“采集接口仍未接受登录（未登录或登录态过期）”，与采集器看到的一致。文档与 CHANGELOG 已同步。

### 内容写入：唯一入口 `LegalCorpusStore.put()`

- 请求先过 `write-contract.ts` 的 `legal-corpus-write/v1` strictObject 校验：`corpus` 仅 `law|cases`、`sourceId` 1-1024 字符、`sha256` 64 位小写十六进制、`bytes` 1 字节至 8 MiB、`mode` 默认 `PUBLISH`、`jobId` 可选且必须匹配 `lcj_` + UUID。校验失败抛 `CORPUS_WRITE_INVALID`。
- 自校验：`digest(bytes) !== sha256` 抛 `CORPUS_BLOB_INTEGRITY`；`search_text` 由正文去掉 front matter 后生成。
- 预检（写 Blob 之前）：带 `jobId` 时任务必须存在且 `RUNNING` 且未请求取消，否则 `CORPUS_JOB_NOT_ACTIVE`；`BACKFILL` 模式要求文档已有 `current_revision_id`，否则 `CORPUS_BACKFILL_REQUIRES_PUBLISHED_DOCUMENT`。
- 幂等重放：已知 `(document_id, sha256)` 时不新增版本，只校验已存对象字节与 hash，对象缺失则按已校验字节补写（restore），按需更新 `search_text`，返回 `changed=false, published=false`，不移动当前指针。
- 新版本路径：`putImmutable` 写 Blob 对象（不可覆盖）→ 事务内再次 `FOR UPDATE` 校验任务 → `PUBLISH` 时 `INSERT la_corpus_documents ON CONFLICT DO NOTHING` 并锁行 → `INSERT la_corpus_revisions ON CONFLICT DO NOTHING` → 仅当新增行且模式为 `PUBLISH` 时 `UPDATE current_revision_id` → COMMIT；任一步失败 ROLLBACK。
- 四个稳定错误码：`CORPUS_WRITE_INVALID`、`CORPUS_BACKFILL_REQUIRES_PUBLISHED_DOCUMENT`、`CORPUS_BLOB_INTEGRITY`、`CORPUS_JOB_NOT_ACTIVE`。

### 写入的两个调用方

- `importer.ts` 的 `importBundle()`：资料包导入。先整体校验 manifest（路径必须 `workspace/{corpus}/` 开头、禁 `log/quarantine`、禁符号链接、数量一致、逐文件 hash 与 stable_id 匹配、单文件 ≤8 MiB），任何校验失败在第一次写库前中止；通过后逐文件读盘复核 hash、解析 front matter、以 `wx` 标志写入维护工作区（不覆盖旧文件）、调 `store.put()`（默认 `PUBLISH`，可传 mode）；案例维护 `cases/log/index.json`；统计 `seen/added/unchanged/failed`。
- `importer.ts` 的 `reconcile()`：采集器输出对账。遍历 `workspace/{corpus}`（跳过 `log/quarantine`），同源去重，逐文件 `store.put()`；单文件失败计入 errors（最多 100 条）不中断，但 `CORPUS_JOB_NOT_ACTIVE` 直接抛出终止。设计上只增不删：缺失文件不会删除已发布记录。

### 任务与调度表的写入（维护边界）

- `CorpusJobs.enqueue()`：`INSERT la_corpus_jobs ... QUEUED`，`idempotency_key` 冲突时 `DO NOTHING`，重复入队幂等。
- `claim()`：仅 Worker 在 advisory lock 下调用；先把残留 `RUNNING` 任务标记 `INTERRUPTED/WORKER_INTERRUPTED`，再把到期且启用的 schedule `FOR UPDATE` 锁行、推进 `next_run_at` 并入队任务，最后 `FOR UPDATE SKIP LOCKED` 领取一个 `QUEUED` 任务置 `RUNNING`。
- `progress()/finish()/cancel()/retry()`：心跳与阶段、终态（`SUCCEEDED/PARTIAL/FAILED/AUTH_REQUIRED/INTERRUPTED/CANCELED` 等）与错误码、协作式取消（`cancel_requested=true`，`put()` 事务内会拒绝写入）、按幂等键重试。

### 读取行为

- HTTP 六个 `@Get`（`controller.ts`），全部要求有效登录且组织绑定，`maintenance` 额外要求组织管理员；响应头固定 `Cache-Control: private, no-store` 与 `X-Content-Type-Options: nosniff`；响应体均过契约 schema 解析。
- `stats`：按 corpus 聚合文档数/版本数与 `collectedAt` 范围，固定返回 `search: KEYWORD_V1` 与 `freshness: SOURCE_SNAPSHOT_NOT_CURRENTLY_VERIFIED`。
- `documents`：目录浏览，过滤（corpus/validityStatus/caseCategory）全部在 SQL 中执行，`after` 游标 + `limit+1` 分页，只返回当前版本。
- `search`：标题与 `search_text` 的 `ILIKE`（用户输入做 `%`/`_` 转义），排序为标题匹配档位 → 短标题优先 → `imported_at DESC` → id；片段取 `search_text` 中首次命中处前后约 400 字符；响应带新鲜度标记。
- `maintenance`：管理员 dashboard（任务列表与计数 + stats），`failurePreview` 只含来源 ID 与稳定错误码，不返回原始 `summary`。
- `revisions`：某文档全部历史版本，按 `imported_at, id` 排序，无记录抛 `NOT_FOUND`。
- `content`：固定版本原文。查 revision 行 → 从 BlobStore 取字节 → 复验 `sha256` 与 `byte_size`，不符抛 `SOURCE_UNRESOLVED`，不返回可能被篡改的内容。
- Agent 工具 `law_search` 只读，走 `store.search()`，返回固定 `documentId/revisionId/sha256`、来源与有界片段；不暴露 BlobStore 路径、维护工作区路径、采集日志或凭据。

### 不变式

- `documentId = lc_ + SHA-256(corpus:sourceId)`；`revisionId = lcr_ + SHA-256(documentId:sha256)`；对象地址 `legal-corpus/{corpus}/{documentId}/{sha256}.md`。
- 版本行不可变（`ON CONFLICT DO NOTHING`），对象不可覆盖；只有 `PUBLISH` 且新增版本才移动 `current_revision_id`；v1 不支持回滚或把历史版本重新发布为当前版本。
