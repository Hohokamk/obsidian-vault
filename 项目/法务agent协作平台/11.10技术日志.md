## 架构与代码

问题：怎么给项目里的 Mastra Agent 接工具（Agent tool）。结论：工具只能挂在“任务 Run”这条 agent 链路上，只读案件助手链路按设计禁止工具。

接入顺序（四步，均按源码现状）：

1. 新建 `apps/server/src/adapters/<name>-tool.ts`，用 `@mastra/core/tools` 的 `createTool` + zod `strictObject` 输入输出 schema，导出工具 id 常量；宿主能力用工厂函数注入（如 `createLawSearchTool(corpus)`），不在模块层取全局依赖。参考 `apps/server/src/adapters/legal-corpus-search-tool.ts`、`draft-document-preflight-tool.ts`。
2. 在 `apps/server/src/adapters/mastra-model.ts` 的 `createMastraModelGateway` 增加可选依赖参数（当前第 4 个参数为 `legalCorpus?: Pick<LegalCorpusStore, 'search'>`），在 `generate` 内按请求条件组装 tools map（`preflightTools` 489 行、`corpusTools` 495 行），并在 instructions 追加一段“何时调用、可引用哪些字段”的说明（`law_search` 说明块在 509-513 行）。
3. tools 只在 `request.workspace` 存在时挂载，`toolChoice` 由 `request.workspace ? 'auto' : 'none'` 决定（521 行）；无工作区的空材料生成仍是单次调用、无工具。
4. 组合根 `apps/server/src/bootstrap.ts` 第 179 行把宿主 store 传进 gateway（现在传 `legalCorpus`，由第 100 行 `new LegalCorpusStore(corpusPool, blobs)` 构造）。

必须遵守的约束（依据源码推断，均已确认存在于现有实现）：

- 隐私外发：每次真正发送前都执行 `beforeProviderCall` → `assertPromptEgressAllowed`；工具结果会作为 tool 消息进入下一步 prompt，所以工具输出的数据类别必须落在配置目标 allowlist 允许的 dataClass（`USER_PROMPT`/`WORKSPACE_MATERIAL`/`MATTER_STATE`/`MATTER_MEMORY_EVIDENCE`/`NAVIGATION`）与允许模式内，否则 `PRIVACY_DENIED`。
- 调用预算：每个工具续跑都是一次 provider invocation，计入 `callLimit`（来自 `maxProviderCalls` 或 `LEGALAGENT_MODEL_MAX_STEPS`），工具不是免费的。
- 输出白名单化：schema 只放模型可引用字段（`documentId`/`revisionId`/`sha256`/`sourceUrl`/有界 `snippet`），`apps/server/test/model.test.ts` 中断言内部字段不会进入续跑请求。
- 诊断只收数值/枚举元数据（`emitDiagnostic`），工具结果可用 `preflightResult` 形式的回调发 `workspace_tool_result`。
- 原生文件工具（`mastra_workspace_read_file` 等）来自 Mastra Workspace，没有 shell 工具。

只读助手链路 `apps/server/src/adapters/mastra-assistant.ts` 明确 `toolChoice: 'none'` 且不传 tools，注释写明 “no Run, feature, workspace, tools…”。要给它接工具等于改设计约束（单次调用、无执行能力），需先定隐私与权限边界。

- 前端（已核对）：`CorpusMaintenancePanel.tsx` 只有“刷新状态”按钮与查看任务失败详情抽屉，没有入队/触发/取消按钮；`CorpusLibrary.tsx` 为检索与固定版本预览。E2E 既有断言：普通成员访问维护路由只看到权限提示且不请求维护接口。
- 采集的真实入口只有运维侧：`npm run corpus:ops -- enqueue` 入队，`corpus:worker` 常驻领取或 `corpus:ops -- once` 单发；案例采集前需 `corpus:ops login` 完成法院站点人工登录；定时任务经 `corpus:ops schedule` 配置，当前未启用（0 行）。写入路径按 `docs/legal-corpus.md` 限定为导入器、维护 Worker 和运维命令三处。
- 若产品要求网页触发采集（设计变更）：需要新增内部写入接口并在契约中从六个只读 GET 扩展或升版本、明确管理员级权限与审计、评估采集任务对业务库的外发与资源边界，并改 E2E 中“无采集按钮”的断言。与当前定位冲突，需先做产品决策，不能靠绕过测试挂载。

同日续（存储方案与 schema 设计讲解，依据源码与实库核对）：

方案一句话：PostgreSQL 存目录、版本、元数据和检索文本，BlobStore 存不可变原文字节；两者用内容寻址的 `object_ref` 关联。四张表：`la_corpus_documents`（目录，`(corpus,source_id)` 唯一）、`la_corpus_revisions`（不可变版本，`(document_id,sha256)` 唯一、`object_ref` 唯一）、`la_corpus_jobs`（维护任务，八种状态）、`la_corpus_schedules`（定时，仅 `LAW_UPDATES`/`CASE_CHECK`，间隔下限 3600 秒）。

ID 与路径规则（服务端生成，调用方不能指定）：`documentId = lc_ + SHA-256(corpus:sourceId)`，`revisionId = lcr_ + SHA-256(documentId:sha256)`，`objectRef = legal-corpus/<corpus>/<documentId>/<sha256>.md`。`la_corpus_documents.current_revision_id` 用复合外键 `(id,current_revision_id)` 保证指针属于同一文档。

写入模型：`PUBLISH` 才移动当前版本指针，`BACKFILL` 只补录历史、不动指针；重放已知 hash 幂等返回 `changed=false`。读取必须指定 documentId + revisionId，返回前重新校验 `byte_size` 与 `sha256`（`store.ts` 的 `content`）。契约 `legal-corpus-v1` 已于 2026-11-05 冻结（`docs/legal-corpus-contract-v1.md`）。

实库核对（2026-11-10）：`metadata` 合计约 9.4 MB、`search_text` 合计约 26 MB，无空 `search_text`；原文对象在 `.local/objects/legal-corpus/{law,cases}/`，law 2,226 个文件 34.8 MB、cases 5,580 个文件 40.8 MB。**新发现**：law 对象数比修订数多 2（7,806 vs 7,804），即存在 2 个未引用对象，与设计中“事务失败产生的未引用对象不对外可见、按保留策略清理”一致，非数据丢失，后续可关注清理策略。
