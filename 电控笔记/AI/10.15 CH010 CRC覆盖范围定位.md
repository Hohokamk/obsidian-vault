# 10.15 CH010 CRC 覆盖范围定位

**简介**：实机现象 `rx_ok=0 / crc_fail 持续涨 / len_bad=0`，最终定位到 **CRC 覆盖范围漏了「帧头 + 长度」4 字节**。手册明确 CRC 是**两段拼接**——`buf[0..3]` + `buf[6..6+len]`，中间的 CRC 字段 `[4..5]` 不参与计算——而旧代码只盖了数据域。修好后用官方手册的样例帧 `5A A5 4C 00 6C 51 91 ...` 端到端验证通过（算得 `0x516C` == 帧内携带值）。顺带发现**旧代码把 gyro 和角度的 roll/pitch 都读反了**，此前"为补偿 90° 安装"是个错误结论，已按手册恢复。

## 二、CRC 覆盖范围：两段拼接，不是整段

### 手册原文

> | CRC校验 | - | 2 | 除 CRC 本身外其余所有字段(帧头, 帧类型, 长度, 数据域)的 16 位 CRC 校验和。LSB(低字节在前) |

### 手册给的校验代码

```c
crc = 0;
crc16_update(&crc, buf, 4);                // 帧头 2B + 长度 2B
crc16_update(&crc, buf + 6, payload_len);  // 数据域
```

**这是两段拼接，中间的 CRC 字段 `buf[4..5]` 被跳过了。**

### 我踩的坑

我第一次把「除 CRC 本身外」理解成"**把 CRC 字段算进去凑自同步**"，于是写了一整段 `Check(rxData, len+6, crc)`。

**两种理解结果完全不同。** 官方样例帧实测：

| 做法 | 结果 |
|---|---|
| 两段拼接 `buf[0..3]` + `buf[6..6+len]` | `0x516C` ✅ 与帧内携带值相同 |
| 一整段 `buf[0..len+5]`（含 CRC 字段） | ❌ 对不上 |

⇒ **「除 CRC 本身外」= CRC 字段不算进去**，不是自同步。

### 实现上的后果

CRC 运算必须**跨调用延续**，所以给 `Check()` 加了累加器参数：

```cpp
bool Check(uint8_t* pdata, uint8_t len, uint32_t com, uint16_t* acc = nullptr);
//                                                        ↑ 传 nullptr = 单段从 0 起算
```

```cpp
uint16_t crc_acc = 0;
if (!Check(rxData,     4u,      crc_raw, &crc_acc)) { ++crc_fail; return; }
if (!Check(rxData + 6, len_raw, crc_raw, &crc_acc)) { ++crc_fail; return; }
```

## 三、CH010 完整帧结构

```
[0]    0x5A        帧头
[1]    0xA5        帧类型
[2..3] LEN (u16 小端)   数据域长度，不含帧头/帧类型/LEN/CRC
[4..5] CRC (u16 小端)   LSB 低字节在前
[6..]  数据域
```

**帧总长 = len + 6**

**算法 = CRC-16/CCITT-FALSE**：poly `0x1021`、init `0x0000`、MSB-first、不反射、无 final xor。与手册的 `crc16_update()` 逐位等价。

⚠️ **与 V2 PC 帧用的 CRC-16/MCRF4XX 是两个不同算法**（那个 init `0xFFFF`、反射表 `0x8408`）。别互相当参照物。

### 与实机数据完全对上

| 项 | 值 | 验证 |
|---|---|---|
| `len` | 76 (`0x4C 00`) | ✅ |
| 帧总长 `len + 6` | 82 | ✅ 与实测 `rx_len = 82` 精确吻合 |
| tag | `0x91` | ✅ |
| `system_time` | 586648 ms ≈ 9.8 min | ✅ 合理的运行时长 |

## 四、0x91 数据包字段表（偏移相对 `p = rxData + 6`）

| 偏移 | 类型 | 大小 | 单位 | 含义 |
|---:|---|---:|---|---|
| 0 | uint8_t | 1 | - | 数据包标签 `0x91` |
| 1 | uint32_t | 4 | - | ID |
| 4 | float | 4 | Pa | 气压（**CH010 无气压计 ⇒ 无意义**） |
| **8** | uint32_t | 4 | **ms** | **本地时间戳，开机累加，每毫秒 +1** ← A 实验基准 |
| 12 | float | 12 | 1G | 加速度 XYZ（出厂校准） |
| 24 | float | 12 | deg/s | 角速度 XYZ |
| 36 | float | 12 | uT | 磁强度 XYZ |
| 48 | float | 12 | deg | Roll(±180) / Pitch(±90) / Yaw(±180) |
| 60 | float | 16 | - | 四元数 WXYZ |

固定 76 字节。

### 🔴 旧代码把轴读反了

```cpp
// ❌ 旧代码
angularvelocity.pitch = R4(p + 24);   // 手册说 24 = X
angularvelocity.roll  = R4(p + 28);   // 手册说 28 = Y
angle.pitch = R4(p + 48);             // 手册说 48 = Roll
angle.roll  = R4(p + 52);             // 手册说 52 = Pitch
```

此前记忆里记的「roll/pitch 对调是**刻意保留**，疑似补偿 IMU 的 90° 安装」——**这是个错误结论**。那只是一处无依据的历史错位，跟安装角度没关系。

已按手册恢复：`roll@24 / pitch@28 / yaw@32`、`roll@48 / pitch@52 / yaw@56`。

⇒ **B 实验（轴标定）的起点变了，之前的静态实验结论要推翻重来。**

### 顺手发现的抓手

**磁强度（`p+36`）在 9 轴模式非零，6 轴模式恒零** ⇒ 这是判 6/9 轴最现成的抓手，比"开电机看 yaw 跳"更直接。

## 六、踩坑记录：改对覆盖范围，却写错了比较时机

改完覆盖范围后立刻翻车 —— 用户反馈「`rxData` 里有数据，但 `angle` 读不到了，之前是正常的」。

### Bug 本体

```cpp
// ❌ 我写的
uint16_t crc_acc = 0;
if (!Check(rxData,     4u,      crc_raw, &crc_acc)) { ++crc_fail; return; }  // ← 这里就 return 了
if (!Check(rxData + 6, len_raw, crc_raw, &crc_acc)) { ++crc_fail; return; }
```

`Check()` 每算完一段就拿自己的结果和 `crc_raw` 比。但**第一段算完的是中间值**（样例帧里 `0x035D`），最终 CRC 是 `0x516C` ⇒ 必然不等 ⇒ 第一行就 `return`，第二段根本没跑，`angle`/`acceleration` 永远不更新。

探针复现（官方样例帧）：

```
=== BUG 版本：每段各自比较 ===
  第一段即 return  <- 字段永不更新
  rx_ok=0 crc_fail=1
```

### 修法：接口层面防误用

```cpp
CrcReset();                        // 每帧从 0 起算
CrcAccum(rxData, 4u);              // buf[0..3]
CrcAccum(rxData + 6, len_raw);     // buf[6..6+len]
if (CrcResult() != crc_raw) { ++crc_fail; return; }
```

三个私有方法**都不暴露比较语义** ⇒ 不可能再写错。`Check()` 恢复成单段语义（给 IMU601 算术和校验用），头文件和 `imu.cpp` 都写了警告。

```
=== 修复版本 ===
  timestamp = 310205 ms
  roll/pitch/yaw = 48.7203 / -21.0144 / -45.5118 deg
  rx_ok=1 sample_ok=1 crc_fail=0
```

## 七、两个更值得记的教训

### 1. 我的错误性质

**这个 bug 的症状和"覆盖范围写错"完全一样**：

| 症状 | 覆盖范围错 | 比较时机错 |
|---|---|---|
| `crc_fail` 涨 | ✅ | ✅ |
| `rx_ok = 0` | ✅ | ✅ |
| `rxData` 有数据但 `angle` 读不到 | ✅ | ✅ |

⇒ 两个 bug 互相掩盖。用户报"angle 读不到"时，我直接以为是覆盖范围没修对，**又去改了代码**。

**收到"改动后出现新症状"的报告，第一反应应该是"我的新改动引入了什么"，而不是"上次没改对"** —— 尤其在同一处连续改了两轮之后。

### 2. 探针必须覆盖「多种调用姿势」

这次探针只验证了"两段拼接算得对不对"，**没验证"用 `if (!Check(seg)) return;` 的姿势调用会怎样"**。

⇒ **累加器型 API 一定要同时测错误用法。** 单次正确调用通过，不代表接口不容易被误用。这类 bug 必然漏到实机。
