# 10.15 IMU/TIM 收尾清理

**简介**：这一轮把 `imu.cpp` 的解码逻辑重构为三个私有分支方法（`DecodeIMU601` / `Decode0x91` / `MarkSampleValid`），修掉三个真实缺陷——IMU601 分支的**越界读**（下标最大 259 而缓冲只有 100 字节）、IMU601 校验长度算错（`len` 是数据组数而非字节数）、以及 IMU601/HI226 两个分支**根本不更新 `init_done`/`last_rx_tick`/`data_ok`**（⇒ 这两种型号下 `IsValid()` 永远 false，`ORIENTATION_VALID` 一直挂）。`tim.cpp` 侧给 `UsInit()` 补 `DIER=0`，并删掉 `timer.counter` 这个每秒被 ISR 空转 1000 次、却已无任何消费者的全局变量。探针 22 项断言全过，ARM GCC 与 MinGW 双侧零警告。

---

## 一、`imu.cpp` / `imu.h`

### 改动结构

```
Decode()                       ← 瘦身：取帧 + 三路分派
├─ DecodeIMU601()              ← 0x55 0x55 家族（len = 数据组数）
├─ Decode0x91()                ← 0x5A 0xA5 家族（CH010 与 HI226 共用同一份实现）
└─ MarkSampleValid()           ← "本帧可用"标记的统一收口
```

把 CH010 和 HI226 合并成 `Decode0x91()` 是关键：**原来两份几乎相同的代码是复制粘贴的，所以一处漏了有效性标记、另一处漏了 timestamp**。合成一份 + 抽 `MarkSampleValid()` 收口，这类漏洞从结构上不再可能发生。

---

## 二、修掉的三个真 bug

### 1. IMU601 分支越界读（真 UB）

```cpp
// ❌ 原代码
Check(rxData, rxData[3] + 4, rxData[rxData[3] + 4])
```

`rxData[3]` 是 `uint8_t`，最坏取 255 ⇒ 末下标 **259**，而 `rxData` 只有 `UART_MAX_LEN = 100` 字节。一帧坏数据就能越界读 159 字节 —— 踩到的可能是别的对象的内存，表现是"随机的姿态跳变"，极难查。

```cpp
// ✅ 现在：先钳位，且明确校验口径
const uint32_t ngrp  = rxData[3];
const uint32_t ndata = ngrp * 6u;      // 数据组数 × 6 B/组
const uint32_t need  = 5u + ndata;     // 4 帧头 + 数据区 + 1 校验
if (ngrp == 0u || need > UART_MAX_LEN) { ++len_bad; return; }
```

### 2. IMU601 校验长度算错（逻辑 bug）

该家族的 `len` 是**数据组数**，每组 3 轴 × 2 B = **6 字节**，所以数据区是 `len*6` 字节。原代码只累加 `len+4` 字节，覆盖不到 1/6 的数据区 ⇒ 校验形同虚设，而且因为漏掉了后半段真实数据，累加值也和模块发的校验和对不上（现象是"帧帧全丢"）。

正确口径：校验和 = 帧头 4 字节 + 数据区 `len*6` 字节 的字节和，校验字节位于 `4 + len*6`。

### 3. 两个分支不更新有效性标记（分支不对称）

`IsValid()` 判的是：

```cpp
return init_done && (xTaskGetTickCount() - last_rx_tick) <= pdMS_TO_TICKS(50) && data_ok;
```

但 **IMU601 和 HI226 分支完全没碰这三个变量** —— 只有 CH010 分支设了。切到这两种型号时 `IsValid()` 永远 false，而 `xuc.cpp` 的 `XUC_F_ORIENT_VALID` 是直接拿它置位的 ⇒ 上位机会一直看到"姿态无效"。

根因就是复制粘贴：CH010 那份是完整写的，另两份是删减版。现在统一走 `MarkSampleValid()`。

## 三、`tim.cpp` / `tim.h`

### 1. `UsInit()` 补 `DIER = 0`

```cpp
TIM2->DIER = 0;   /* 🔴 强制清中断使能 */
```

若 TIM2 之前被 `HAL_TIM_Base_Init` 过（会回调 `HAL_TIM_Base_MspInit` → 开 TIM2 NVIC），残留的 `UIE` 会让 1 MHz 计数器**每秒产生 100 万次中断请求**直接拖死系统。这里不碰 NVIC，只保证外设侧不再产生中断。

### 2. 删掉 `timer.counter`

```cpp
// ❌ 原代码
if (timer.counter++, timer == htim) { /* 空 */ }
```

- 它是**全局变量**，被所有 TIM 实例的 ISR 共享累加
- 唯一消费者（`CanTransimtTask` 的 `%3` 分频）已经改成任务私有 `static uint8_t can_div`
- 现在纯粹是 TIM3 1 kHz 中断里白跑一次读改写

连带删掉 `tim.h` 的 `uint32_t counter` 成员。**留着它就是留一个"看起来在用、实际没人读"的共享全局变量**，以后谁再写 `timer.counter++` 会重新引入 ISR/任务竞争。

⚠️ 连带结论：TIM3 现在挂着一个 **1 kHz 空中断**（`timer.Init(BASE, TIM3, 1000).BaseInit()`）。如果确认无消费者，这句连同 `BaseInit()` 可以整条去掉 —— 但要改 `STM32F405.cpp`，需另行授权。

## 四、🔴 探针踩到的 `sizeof` 陷阱（最值得记的一条）

初版探针把解码函数写成这样：

```cpp
static void Decode0x91(Sense& s) {
    uint8_t* rxData = s.rxData;              // ← 指针别名！
    if (len_raw > (sizeof(rxData) - 6u)) ...  // sizeof(指针) = 8，不是 100
}
```

结果 `len_raw > 2` 就误判，**所有正常帧全被丢弃** —— 22 项测试红了 13 项，一度以为是 CRC 改错了。

真实固件里 `rxData` 是数组成员，`sizeof(rxData)` 本来是对的，**所以这个 bug 只存在于探针里、固件是干净的**。但这暴露了写法的脆弱性，已把两处长度上界都改成显式常量：

```cpp
if (len_raw == 0u || len_raw > (UART_MAX_LEN - 6u))   // 不再写 sizeof(rxData)
```

**教训**：容器长度上界永远写**类型对应的常量**（`UART_MAX_LEN`），不要写 `sizeof(某个局部指针别名)` —— 后者今天对、以后有人改成指针就静默错一个数量级，且不会报任何错。

## 五、CRC 口径澄清（避免以后混用）

`imu.cpp::Check` 的注释原来写「CRC-16/MCRF4XX」是**错的**。实际两个协议用两个不同算法：

| | IMU `0x5A 0xA5` 帧 | V2 PC 帧（`CRC.h`） |
|---|---|---|
| 算法 | CRC-16/CCITT-FALSE | CRC-16/MCRF4XX |
| init | `0x0000` | `0xFFFF` |
| 多项式 | `0x1021` | 反射表 `0x8408` |
| 方向 | MSB-first | 反射（LSB-first） |
| final xor | 无 | 无 |
| 覆盖 | `rxData+6` 起 `len` 字节 | 帧头 + 完整 payload（`len-2`） |
| 实现 | `imu.cpp::Check`（逐位） | `CRC.cpp`（查表） |

**init 都不同、覆盖范围也不同，别互相当参照物。** 已修正 `Check()` 的注释。

## 六、新增诊断计数

| 计数 | 含义 |
|---|---|
| `rx_ok` | 帧头 + 长度 + CRC 全部通过 |
| `crc_fail` | CRC 不匹配 |
| `len_bad` | 长度字段非法（0 或越界） |
| `sample_ok` | **`0x91` 姿态包**通过 CRC 的帧数 |
| `short_payload` | 是 0x91 包但 `len < 60`，读不到 yaw 就丢弃 |

⚠️ **A 实验做线性回归要用 `sample_ok` 当分母，不能用 `rx_ok`** —— 后者含"帧有效但不是 0x91 姿态包"的帧（比如其他 type 的状态包），那些帧没有可用于标定的 `timestamp`，混进去会污染样本集。

### `short_payload` 为什么要单独一道

**CRC 合法 ≠ 内容够长。** 一帧 `len=20` 的 0x91 包能通过 CRC（因为 CRC 就只覆盖那 20 字节），但代码要读 offset 56 的 yaw（占 56..59）⇒ 需要 payload 至少 60 字节。不卡这一道就是越界读。

这道检查放在「上界钳位」之后，是**独立**的一道，两个都要。

## 七、探针复验结果（22 项断言全过）

| 场景 | 断言 |
|---|---|
| 正常 0x91 帧 | `timestamp`/三个角度/三个加速度逐项正确、`init_done` 置位 |
| 连续 8 帧 | 8/8 通过、`crc_fail=0`（回归"跨帧累积"这个老 bug） |
| 篡改 payload 一位 | 必检出（`crc_fail=1`、`sample_ok=0`） |
| `len=284` | 判 `len_bad` 丢弃，**不静默截断成 28** |
| `len=20`（CRC 合法） | 被 `short_payload` 拦下，且**未误标** `init_done` |
| `type=0x90` 有效帧 | 计 `rx_ok`、不计 `sample_ok` |
| IMU601 `len=250` | 判 `len_bad`，**未越界读** |
| IMU601 正常角度帧 | `init_done`/`data_ok` 正确置位 |

编译：MinGW `-Wall -Wextra` 零警告跑通；ARM GCC 10.3.1 `-O2 -Wall -Wextra -Wparentheses` 零警告。探针文件用完已删。
